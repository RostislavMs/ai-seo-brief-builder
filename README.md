# AI SEO Brief Builder

Сервіс аналізує сторінки конкурентів за URL, витягує з них лише основний контент
і формує на його основі детальне SEO ТЗ для написання статті. Ті самі дані
відповідають на друге питання — [чого бракує вашій уже наявній
сторінці](#аналіз-власної-сторінки) проти цих конкурентів. Готове ТЗ можна
[відкрити за посиланням](#публічне-посилання) без входу — райтерові або клієнту.

Повне ТЗ проєкту — [ТЗ.md](ТЗ.md).

## Структура

```text
apps/web              Фронтенд: Vite + React 19 + React Router 8 + Tailwind 4
apps/server           Бекенд: Nitro 2 (рантайм) + Hono 4 (маршрути та логіка API)
packages/shared       TypeScript-типи, каталог AI-моделей і реєстр мов
supabase/migrations   SQL-схема: акаунти, сесії, ключі AI, правила, публічні посилання
```

У продакшені `apps/server` роздає ще й зібраний фронт: один сервер, одне
походження, жодного CORS — див. [Деплой на Vercel](#деплой-на-vercel).

`packages/shared` підключається як `@brief/shared` і читається напряму з
джерел — окремий білд не потрібен. Якщо змінити тип у ньому, обидві сторони
одразу побачать помилку на `pnpm typecheck`.

## Запуск

```bash
pnpm install          # один раз
pnpm dev              # фронт + бекенд разом
```

- фронт — <http://localhost:5173>
- бекенд — <http://localhost:3000>

Відкривати треба **5173**. Фронт звертається до відносного `/api/*`, а Vite
проксює ці запити на Nitro (`apps/web/vite.config.ts`). Тому в браузері немає
CORS і ніде не захардкоджена адреса бекенда.

Окремо, якщо потрібно:

```bash
pnpm dev:web
pnpm dev:server
```

## Налаштування Supabase

Авторизація та зберігання сесій живуть у Supabase. Без нього працює лише
`/api/health` — решта маршрутів віддає 503 із поясненням.

**1. Накотити схему.** Supabase Dashboard → SQL Editor → виконати по черзі
[0001_init.sql](supabase/migrations/0001_init.sql),
[0002_drop_brief_language.sql](supabase/migrations/0002_drop_brief_language.sql),
[0003_language_rules.sql](supabase/migrations/0003_language_rules.sql),
[0004_own_page.sql](supabase/migrations/0004_own_page.sql),
[0005_session_language.sql](supabase/migrations/0005_session_language.sql),
[0006_prompt_templates.sql](supabase/migrations/0006_prompt_templates.sql),
[0007_analysis_excluded.sql](supabase/migrations/0007_analysis_excluded.sql),
[0008_session_shares.sql](supabase/migrations/0008_session_shares.sql),
[0009_user_fetch_keys.sql](supabase/migrations/0009_user_fetch_keys.sql),
[0010_brief_edits.sql](supabase/migrations/0010_brief_edits.sql).
Скрипти ідемпотентні, повторний запуск нічого не ламає. Поки цього не
зроблено, застосунок показує на головній: «Потрібної таблиці немає в базі».

Порядок має значення на деплої: `0010` додає колонку, яку сервер читає в
кожному запиті сесії, тому котити її треба **до** того, як піде новий код, —
інакше сесія не відкриється взагалі.

Винятки — `0008` і `0009`: без них решта працює як раніше. Без `0008` 503
відповідає лише публікація; без `0009` список ключів сервісів доступу просто
порожній (і каскад обходиться безкоштовними ступенями), а 503 приходить тільки
на спробу такий ключ додати. Так зроблено навмисно: обидві — додаткові
можливості, а не частина основного шляху, і непрокочена міграція не має робити
застосунок неробочим.

**2. Змінні оточення.**

```bash
cp apps/server/.env.example apps/server/.env
cp apps/web/.env.example    apps/web/.env
```

| Змінна | Де взяти |
| --- | --- |
| `NITRO_SUPABASE_URL` | Dashboard → Project Settings → API |
| `NITRO_SUPABASE_SECRET_KEY` | там само, secret key (`sb_secret_…`) |
| `NITRO_ENCRYPTION_KEY` | `openssl rand -hex 32` |
| `VITE_SUPABASE_URL` | той самий URL проєкту |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | publishable key (`sb_publishable_…`) |
| `NITRO_ADMIN_EMAILS` | необов'язково: пошти адміністраторів через кому |

Secret-ключ обходить RLS і у фронт не потрапляє ніколи. Publishable-ключ,
навпаки, публічний за задумом — він у бандлі, і це нормально.

`NITRO_ENCRYPTION_KEY` шифрує ключі користувачів — і AI-провайдерів
(`user_ai_keys`), і платних сервісів доступу до сторінок (`user_fetch_keys`).
Якщо його змінити, збережені ключі стануть нечитабельними, і кожен користувач
побачить прохання додати ключ заново.

**3. Підтвердження пошти.** За замовчуванням Supabase вимагає підтвердити
адресу, а вбудований поштовий сервіс має жорсткий ліміт (кілька листів на
годину). Для локальної розробки: Authentication → Providers → Email →
вимкнути «Confirm email». Для продакшену — підключити власний SMTP.

## Ключі AI

Кожен користувач додає власний ключ у **Налаштування → AI-провайдери**:
Gemini, OpenAI або Claude. Ключ перевіряється живим запитом до провайдера,
шифрується (AES-256-GCM) і більше ніколи не повертається в браузер.

**Ключа AI на сервері немає.** У `.env` його не існує як змінної: спільний
ключ означав би спільний ліміт і чужий рахунок за токени, а «демо-режим»
рано чи пізно стає режимом за замовчуванням. Немає ключа — `/api/brief` і
`/api/chat` віддають 503 з поясненням; парсинг сторінок при цьому працює.

Той самий принцип поширено й на доступ до сторінок: у **Налаштування → Доступ до
закритих сторінок** користувач може додати ключ Firecrawl, і тоді каскад
отримує ще одну платну ступінь за його рахунок — див.
[ступінь 6](#firecrawl-ступінь-6). Різниця з AI одна: без цього ключа сервіс
працює повністю, лише частина найзакритіших сторінок дістається архівом замість
свіжого контенту.

Змінні `.env` мапляться на `runtimeConfig` з `apps/server/nitro.config.ts`
за префіксом `NITRO_`: `NITRO_FETCH_TIMEOUT_MS` → `runtimeConfig.fetchTimeoutMs`.
Читати їх треба лише через `getConfig()` з `apps/server/src/config.ts`.

Індикатор у правому верхньому куті показує, чи бачить фронт бекенд; рядок
під списком сесій — яка модель зараз обслуговує запити.

## Перевірки

```bash
pnpm typecheck        # tsc по всіх трьох пакетах
pnpm build            # прод-білд фронта, потім бекенда
pnpm preview          # зібраний застосунок цілком: http://localhost:3000
```

Порядок у `build` не випадковий: Nitro забирає `apps/web/dist` до себе, тому
фронт збирається першим. `pnpm preview` підіймає один сервер, який роздає
і фронт, і API — рівно так, як воно працює в продакшені.

## Деплой на Vercel

**Один проєкт Vercel, не два.** Фронт звертається до відносного `/api/*`, тому
статика й API мають жити на одному походженні. Nitro роздає і те, і те:
зібраний `apps/web/dist` підключений як `publicAssets` у
[nitro.config.ts](apps/server/nitro.config.ts), а глибокі посилання SPA
(`/sessions/:id`) віддає [routes/[...].ts](apps/server/routes/%5B...%5D.ts) —
без нього перезавантаження такої сторінки дало б 404.

**1. Налаштування проєкту.** Import репозиторію → Settings:

| Поле | Значення |
| --- | --- |
| Root Directory | `apps/server` |
| Node.js Version | 22.x |

Install і build команди задані в [vercel.json](apps/server/vercel.json) — обидві
виконуються з кореня монорепозиторію, бо `pnpm` має поставити всі три пакети.
Presets Nitro визначає сам за змінною `VERCEL`, вказувати його не потрібно.

**2. Змінні оточення.** Ті самі, що й локально, — Settings → Environment
Variables, для всіх оточень:

```text
NITRO_SUPABASE_URL           NITRO_ENCRYPTION_KEY
NITRO_SUPABASE_SECRET_KEY    NITRO_ADMIN_EMAILS     (необов'язково)
VITE_SUPABASE_URL            VITE_SUPABASE_PUBLISHABLE_KEY
NITRO_READER_KEY             (необов'язково; знімає ліміт частоти ступеня 3)
NITRO_PROXY_URL              (необов'язково)
```

`VITE_*` потрібні саме на етапі складання: вони запікаються в бандл. Змінити їх
без нового деплою не вийде.

**3. Supabase.** Накотити [міграції](supabase/migrations) на продакшн-проєкт і
додати домен деплою в Authentication → URL Configuration (Site URL і Redirect
URLs). Посилання підтвердження пошти й скидання пароля ведуть на
`${origin}/login` та `${origin}/reset-password`; поки домену немає в списку,
Supabase їх не відпрацює.

### Що на Vercel працює інакше

| | Локально | На Vercel | Чому |
| --- | --- | --- | --- |
| Ступінь 2 каскаду — Chrome | ✅ | ❌ | у serverless немає ні встановленого браузера, ні права його запустити |
| Ступінь 9 — копія архіву на вимогу | ✅ | ❌ | очікування копії (~20–40 с) не влазить у ліміт тривалості функції |
| Бюджет часу на сторінку | 150 с | 120 с | межу диктує `maxDuration` функції, а не терпіння користувача |

Обидві ступені вимикаються автоматично під час складання на Vercel, вручну
нічого не треба. [Каскад доступу](#доступ-до-сторінок) лишається робочим:
ступінь 3 — [зовнішній сервіс читання](#сервіс-читання-ступені-3-і-8) — рендерить
JavaScript і обходить захист без нашого браузера, тому саме вона там і замінює
ступінь 2. Повернути вимкнене можна змінними `NITRO_BROWSER_ENABLED=true` і
`NITRO_ARCHIVE_ON_DEMAND_ENABLED=true`, але без встановленого Chrome перша
з них лише додасть до кожного аналізу зайву спробу.

`maxDuration` функції — 300 с: це стеля [Fluid compute](https://vercel.com/docs/functions/configuring-functions/duration)
(увімкнений за замовчуванням) і на Hobby, і на Pro — там вона водночас
і default, і максимум. Pro може більше (800 с, поштучно до 1800), але потреби
немає: реальну межу тримає `NITRO_AI_BUDGET_MS` — 280 с.

### jsdom зафіксований на 26.x

Не оновлювати без перевірки на Vercel. З 27-ї версії jsdom залежить від
`@exodus/bytes` — чистого ESM, до якого CommonJS-пакети (`html-encoding-sniffer`,
`whatwg-url`) звертаються через `require()`. Node таке дозволяє з 22.12, а
завантажувач модулів Vercel — ні, і кожен запит до API падає з
`ERR_REQUIRE_ESM` ще до входу в маршрут: jsdom вантажиться разом з усім API
одним чанком, тому вмирає навіть `/api/health`.

Забандлити цю межу замість зовнішніх модулів не вийшло: інлайн jsdom тягне за
собою інлайн усього дерева залежностей, а там ламається interop інших
CommonJS-пакетів (`util.inherits` у `jws` із ланцюжка `@google/genai`).

Поведінку завантажувача Vercel можна відтворити локально — прапорець вимикає
`require(esm)` у Node так само, як це робить платформа:

```bash
NITRO_PRESET=vercel pnpm --filter @brief/server build
cd apps/server/.vercel/output/functions/__fallback.func
node --no-experimental-require-module -e "import('./index.mjs')"   # + справжній запит
```

Перевіряти саме запитом, а не імпортом: Nitro вантажить обробники маршрутів
ліниво, тому на імпорті помилка не проявляється.

## Як це працює

Ключова архітектурна межа: **AI ніколи не бачить HTML**. Пайплайн такий:

```text
URL → fetch → метадані + JSON-LD → очищення обвісу → вибір джерела контенту
    → Cheerio дістає структуру → ParsedPage (JSON)
    → промпт → Gemini / OpenAI / Claude → SeoBrief (JSON) → UI
```

Той самий пайплайн обслуговує другий сценарій — [порівняння власної
сторінки](#аналіз-власної-сторінки) з тими самими конкурентами.

Сесії, ТЗ і зашифровані ключі провайдерів зберігаються в Supabase й
привʼязані до акаунта.

### Не всі розібрані сторінки йдуть у ТЗ

Каскад доступу витягує контент майже завжди, але «витягнуто» не означає
«годиться»: серед десяти адрес трапляється форумна гілка замість статті,
лістинг категорії або сторінка не про ту тему. Досі такий рядок або лишався
в промпті й тягнув ТЗ за собою, або доводилося створювати сесію заново без
нього — разом із повторним парсингом усіх решти.

Тому кожна успішно розібрана сторінка у вкладці «Аналіз» має чекбокс. Знята
позначка (`session_analyses.excluded`, міграція 0007) означає, що сторінка
лишається в сесії разом із розібраним контентом — її видно, її можна
розгорнути, — але в промпт вона не йде. Повернути її в роботу можна будь-коли
й **без повторного аналізу**.

Виключення діє на всі три сценарії — генерацію ТЗ, правки через чат і
порівняння власної сторінки, — а не лише на ТЗ. Прапорець означає «ця сторінка
не годиться як зразок», а не «не потрібна саме тут»: сторінка, яку не варто
брати за основу ТЗ, так само не варта того, щоб проти неї міряли власну. Одна
умова на всі виклики живе в
[@brief/shared](packages/shared/src/utils/analyses.ts) — розійтися тут означало б
показувати «8 сторінок», а складати ТЗ із семи, і не мати способу це побачити.
У спільному пакеті, а не в `apps/web`, вона саме тому: зліпок публічної версії
збирає сервер, і власна копія цієї умови на його боці була б рівно таким
розходженням, тільки невидимим з інтерфейсу.

Дві дрібниці, які видно лише в коді:

- **Чекбокс — сусід кнопки розкриття, а не її вміст.** Інтерактивний елемент
  усередині `<button>` не працює ні мишкою, ні з клавіатури, тому рядок
  складається з двох цілей. Дії й справді різні: «подивитися, що звідси взяли»
  і «не брати звідси нічого».
- **Прапорець пишеться окремим PATCH без `page`.** Той самий маршрут
  збереження результату парсингу, але з частковим тілом: гнати в базу сотні
  кілобайт розібраного контенту заради одного boolean немає сенсу.

Кількість у бейджі вкладки «Аналіз» лишається кількістю **розібраних** сторінок:
скільком URL узагалі вдалося дістати контент — окреме питання, і виключення
сторінки його не скасовує. А от кнопка генерації ТЗ гаситься саме по
невиключених.

Той самий відбір визначає й список конкурентів у самому ТЗ. У референсних
документах він стоїть першим блоком — «Competitors you need to read» — бо це
перше, що райтер робить: читає конкурентів, а вже потім пише. Вкладки «Аналіз»
він не бачить, тому список повторюється у вкладці «SEO ТЗ» і в скопійованому
документі, і містить тільки те, що реально пішло в промпт: виключену сторінку
давати читати нема підстав. Береться `finalUrl`, а не введена адреса, — після
редиректу райтер має відкрити ту сторінку, яку читала модель.

Належить він сесії, а не ТЗ, тому й передається окремим аргументом у
[`briefPayload()`](apps/web/src/lib/briefDocument.ts): у `SeoBrief` лишається
лише те, що написала модель, а адрес вона не обирала. За публічним посиланням
список береться зі зліпка — якщо автор не публікував розбір сторінок, адрес
у зліпку немає, і блок не виводиться взагалі.

### Чому Readability не головний інструмент

Readability добре відкидає обвіс, але агресивно ріже саму розмітку. На заміряному
прикладі — стаття у Вікіпедії з 13 H2 і 9 H3 — він повернув **нуль заголовків і
нуль таблиць**: заголовки там обгорнуті в `<div class="mw-heading">`, і його
`_cleanConditionally` викидає ці блоки як «мало тексту, багато посилань». Для
SEO-аналізу це фатально, бо структура конкурента і є головним результатом.

Тому [parser/index.ts](apps/server/src/services/parser/index.ts) обирає джерело
залежно від розмітки сторінки:

| Сторінка має | Джерело структури | Readability |
| --- | --- | --- |
| `<article>`, `<main>`, `role=main` | цей контейнер напряму | не запускається |
| немає семантичного контейнера | вивід Readability | запускається |
| Readability не розібрав | найкращий контейнер за класами / `<body>` | — |

Побічний ефект: на сторінках із семантичною розміткою пайплайн не піднімає JSDOM
взагалі, і аналіз пришвидшується приблизно в шість разів (2969 мс → 483 мс).

### Перевірено на реальних сторінках

| Сторінка | Заголовки | Абзаци | Списки | Таблиці | FAQ |
| --- | --- | --- | --- | --- | --- |
| Вікіпедія (uk) | 21 | 34 | 9 | 0 | 0 |
| MDN | 35 | 95 | 1 | 3 | 0 |
| ahrefs.com/blog | 31 | 86 | 5 | 0 | 4 |

Помилки повертаються по-URL і не зривають решту: невалідний URL, локальна адреса,
404, не-HTML, таймаут.

## Доступ до сторінок

Головна практична складність проєкту: сайти конкурентів закриті від ботів.
Тому [acquire.ts](apps/server/src/services/fetcher/acquire.ts) пробує стратегії
послідовно, поки одна не дасть придатний контент.

Порядок — від безкоштовного й швидкого до платного й повільного, а застаріла
копія з архіву стоїть після всього. Це не лише про гроші: **архів майже завжди
щось віддає**, і якби він стояв раніше, каскад закінчувався б на ньому, навіть
коли свіжий контент доступний наступною ступенем.

| | Ступінь | Час | Що дає |
| --- | --- | --- | --- |
| 1 | прямий запит | ~0.3 с | більшість сайтів |
| 2 | справжній Chrome | ~2–7 с | JS-сайти та захист від автоматизації |
| 3 | [сервіс читання](#сервіс-читання-ступені-3-і-8) | ~1–7 с | чужий браузер із чужих адрес; єдиний рендер на Vercel |
| 4 | [той самий запит через проксі](#проксі-ступені-4-і-5) | ~1 с | блокування за діапазоном хостингу |
| 5 | Chrome через проксі | ~6 с | челендж + чужа адреса |
| 6 | [Firecrawl](#firecrawl-ступінь-6) | ~5–16 с | те саме, що 7, але ключем користувача |
| 7 | [API рендерингу](#api-рендерингу-ступінь-7) | ~5–10 с | чужий браузер із чужої резидентної адреси |
| 8 | сервіс читання його адресами | ~5–30 с | те саме, але без свого браузера |
| 9 | наявна копія Wayback | ~2–12 с | те, що не береться нічим іншим |
| 10 | [копія на вимогу](#копія-на-вимогу) | ~20–40 с | сайти, яких немає навіть в архіві |

Ступені 1–3 безкоштовні, 4–8 витрачають гроші й **без налаштувань просто не
виконуються**, 9–10 безкоштовні, але їхній контент може бути застарілим.

Порядок платної частини — за заміряною результативністю, а не за ціною: див.
[ступінь 7](#api-рендерингу-ступінь-7). Виняток — пара 6 і 7: вони роблять те
саме різними сервісами, і порядок між ними визначає не сила, а рахунок. Ступінь
6 працює ключем **самого користувача**, ступінь 7 — спільним серверним, тому
першою пробується та, за яку платить той, хто просив аналіз.

Заміряно наскрізним прогоном на 8 захищених сайтах (g2, forbes, rozetka,
zillow, glassdoor, crunchbase, trustpilot, MDN) **без жодної платної ступені**:
**7 придатних із 8**, з них архівом — 2. До появи ступеня 3 і виправлення
[«код відповіді — не вердикт»](#три-речі-які-виявилися-неочевидними) архівом
віддавалися **4 з 8**: zillow і trustpilot тепер приходять свіжими (1857 і
3507 слів), хоч раніше обидва діставалися лише копією.

Другий прогін — на чотирьох сторінках із
[гейтом Turnstile](#гейт-із-turnstile-коли-не-допоможе-жоден-проксі), де
безкоштовні ступені не можуть нічого в принципі: з увімкненою ступенем 7 три
з чотирьох приходять свіжими (5837, 4806 і 2863 слова), а четверта — з архіву,
і це правильно, бо самої сторінки більше не існує.

### Сервіс читання: ступені 3 і 8

Найсильніша безкоштовна ступінь і головна відповідь на «сайт закритий»:
[r.jina.ai](https://jina.ai/reader) відкриває сторінку **своїм** браузером із
**своїх** адрес, а для нас це один HTTP-запит. Тобто ми отримуємо і рендеринг
JavaScript, і чужий IP там, де свого браузера немає в принципі — на Vercel це
єдина ступінь, що взагалі щось рендерить.

Заміряно на сайтах, де все інше безкоштовне впало: forbes.com — 5628 слів,
zillow.com — 2230, trustpilot.com — 3099. Ті самі сторінки прямим запитом
віддають 403 і 7–25 слів заслонки.

**Режим важливий: markdown, а не HTML.** У сервісу є `X-Return-Format: html`, і
він швидший, але заміряно, що віддає сирий вихлоп першої ж спроби — на zillow це
7 слів заслонки замість 2230 слів тексту. Повний конвеєр сервісу (з повторами й
обходом захисту) працює лише в режимі markdown. Тому markdown повертається в
HTML ([markdown.ts](apps/server/src/services/fetcher/markdown.ts)) — і це не
втрата, а навпаки: у ньому вже немає ні меню, ні банерів, ні скриптів, тобто
рівно того, що [clean.ts](apps/server/src/services/parser/clean.ts) інакше
вирізав би сам. Контент обгортається в `<article>`, тому парсер довіряє йому
напряму й не піднімає JSDOM.

Запит іде в режимі JSON, а не тексту: у ньому окремими полями приходять `title`
й `description`, а вони потрібні для SEO-аналізу так само, як сам текст.

```bash
NITRO_READER_KEY=jina_…          # необов'язково
NITRO_READER_ENABLED=false       # вимкнути ступінь
```

Без ключа ліміт — близько 20 запитів на хвилину на IP сервера, далі сервіс
відповідає `401` (не `429` — тому повідомлення про це окреме, інакше користувач
шукав би проблему в налаштуваннях, яких у нього немає). Ключ видається
безкоштовно, знімає ліміт і додатково відкриває **ступінь 8** — те саме читання,
але резидентними адресами самого сервісу; без ключа вона відповідає `401
AuthenticationRequiredError (Proxy allocation)` і тому не виконується.

Одне застереження: у цьому режимі адреси сторінок, які аналізують, передаються
третій стороні. Кому це не підходить — `NITRO_READER_ENABLED=false`.

### Проксі: ступені 4 і 5

Найчастіше блокування персональне не до нас, а до всієї підмережі: WAF закриває
діапазони дата-центрів цілком. Тому сторінка, яка в браузері відкривається,
з хостингу віддає 403 — і жодні заголовки цього не змінять, бо справа в IP.
Ступінь 4 повторює той самий прямий запит, але через проксі.

Ступінь стоїть **після** всіх безкоштовних навмисно — це відповідь на «проксі
не дав великої результативності». Заміряно: із восьми захищених сайтів шість
беруться безкоштовними ступенями, і платити за них означало б платити даремно.

```bash
NITRO_PROXY_URL=http://логін:пароль@gate.provider.com:8000
NITRO_PROXY_TIMEOUT_MS=25000   # необов'язково
```

Потрібен саме **HTTP**-порт провайдера (у кабінетах його інколи звуть
«HTTPS»). SOCKS5 не підтримується: undici тунелює запит методом CONNECT, а
Chromium не вміє логін-пароль до SOCKS5. Країна й номер сесії в резидентних
провайдерів задаються в логіні (`user-country-de-session-a1b2`) — логін
вставляється як є. Символи `@` і `:` у паролі треба закодувати (`%40`, `%3A`),
інакше URL розбереться не так.

**Трафік платний, тому ступінь не є транспортом за замовчуванням.** Вона
запускається лише після всіх безкоштовних ступенів і лише коли інший IP справді
може щось змінити: на 403, 429 і обриви з'єднання — але не на 404 (сторінки
немає ні для кого) і не на JS-сторінку без тексту (з іншого IP прийде той
самий каркас). Порядок величин при тарифі $1.25/ГБ: HTML статті стисненим
важить сотні кілобайтів, тобто гігабайта хапає на кілька тисяч сторінок.

**Браузер ходить двічі, і перший раз — завжди з нашого IP** (ступінь 2), навіть
коли прямий запит уже впіймав 403. Спокуса одразу піти через проксі виглядає
логічною, але вона хибна з двох боків. По-перше, браузер міняє результат іншим:
він виконує JavaScript і проходить челендж. По-друге, репутація адреси важить
окремо — спільний проксі-IP челенджу підозріліший за домашній. Другий раз
(ступінь 5) той самий браузер іде вже через проксі, і лише проти челенджу: це
найдорожча спроба з наших власних.

Проксі задається на **контекст**, а не на запуск: екземпляр браузера спільний
для всього процесу, і платити за нього мають лише ті сторінки, які інакше не
беруться.

**Чого проксі не лікує.** Заміряно на трьох сторінках із заслонкою
«Verifying…»: прямий запит отримує той самий `403` і з адреси хостингу, і з
резидентної італійської — байт у байт. Це не блокування за діапазоном, а
JS-челендж, і адреса для нього не має значення; допомагає тільки справжній
браузер. Так само не лікується сторінка, яку прибрали: parasite-публікації на
новинних доменах віддають заглушку однаково з будь-якого IP, і архів для них не
костиль, а єдине джерело.

Тобто проксі закриває один конкретний випадок — коли сайт судить саме за
адресою. Це реальний і поширений випадок, але не той, у якому найчастіше
опиняються сторінки з челенджем.

#### Гейт із Turnstile: коли не допоможе жоден проксі

Окремий клас, на який варто вміти дивитися, бо ззовні він виглядає як «поганий
проксі». Розібрано на `premiumtimesng.com/casino/it/malta/` та двох її сусідах.

Сайт не покладається на евристику WAF, а сам ставить браслет Turnstile: **будь-який**
запит отримує `403` і сторінку на десять слів, у якій лише віджет
`data-sitekey="0x4AAA…"`. Розвʼязок токена йде POST-ом на `<каталог>/__ts`, і
лише після нього сторінка перезавантажується з контентом. Заміряно матрицю
4 UA × 2 мови × 2 адреси (наша українська і резидентна італійська Telecom Italia,
`proxy: false, hosting: false` за ip-api) — **`403` у всіх шістнадцяти**
комбінаціях. Проксі при цьому справний: він змінює саму відповідь (з нашої
адреси приходить челендж, з італійської інколи «Access denied.» на 14 байтів),
але жодного разу не контент.

Дві деталі, які варто знати:

- **Сайт визначає headless до челенджу.** З UA `HeadlessChrome/…` приходить
  порожній `403` на два слова — віджета там немає взагалі. Із підміненим на
  `Chrome` приходить сторінка з віджетом. Тобто наша заміна UA працює, але
  далі віджет у headless просто не монтується: кадрів `challenges.cloudflare.com`
  нуль, токен не зʼявляється й за 35 с.
- **Видимий Chrome доходить далі, але теж не проходить.** Кадр челенджу
  зʼявляється (1 iframe), а токен так і лишається порожнім. Клік по віджету
  нічого не змінює.

Отже для такого гейту працює одне з двох: **API рендерингу** (ступінь 6 або 7)
із провайдером, який має власний обхід, або **архів**.

Перевірено на ScraperAPI — [ступінь 7](#api-рендерингу-ступінь-7) цей гейт
пробиває, і свіжий контент виходить повніший за архівний:

| Сторінка | Ступінь 7 | Архів |
| --- | --- | --- |
| premiumtimesng | 5837 слів, H=67, FAQ=18 | 5782 слова, копія за січень |
| completesports | 2863 слова, H=51, FAQ=13 | 2863 слова, копія за січень |
| game-experience.it | 4854 слова | 619 слів |

Ще одна з чотирьох, `punchng.com`, віддає заглушку «AVVERTENZA - SITO NON
RAGGIUNGIBILE» на 91 слово з будь-якої адреси й будь-яким способом, включно з
API рендерингу: сторінки більше немає, і архів для неї — єдине джерело, а не
костиль. Каскад так і вирішує: три сторінки бере ступінь 7, четверту — архів.

Що зробила кожна ступінь, видно в логу сервера — рядок `[fetch] URL → джерело;
до того: …` пишеться щоразу, коли якась ступінь відмовила. Без нього
діагностика зникала саме там, де потрібна: перелік спроб потрапляє в текст
помилки, а коли архів усе-таки дав результат, помилки немає — і причина
відмови проксі нікуди не писалась.

Джерело видно в інтерфейсі окремою міткою «проксі» — інакше не було б як
зрозуміти, які саме сторінки витрачали платний трафік. Пул тунелів живе один
на процес і закривається хуком у
[plugins/shutdown.ts](apps/server/plugins/shutdown.ts).

### Firecrawl: ступінь 6

Те саме, що ступінь 7, — чужий браузер із чужої резидентної адреси одним
запитом, — але **ключем самого користувача**. Це єдина платна ступінь, яку не
налаштовує власник сервера: ключ додається в інтерфейсі, шифрується в
`user_fetch_keys` тим самим `NITRO_ENCRYPTION_KEY`, що й ключі AI, і читається
на кожен запит `/api/analyze`. Немає ключа — ступінь просто не виконується, і це
звичайний стан: решта каскаду від неї не залежить.

**Чому вона перед ступенем 7, хоч слабшою не є.** Порядок тут визначає не сила,
а рахунок. Ступінь 7 працює спільним серверним ключем — тобто за важкі сторінки
одного користувача платять усі; ступінь 6 витрачає кредити того, хто попросив
аналіз. Витрачати чужі раніше за власні неправильно, тому першою йде 6, і коли
вона спрацювала, за наступну не платить ніхто.

Заміряно на двох сторінках, які прямим запитом віддають `403`. Числа — вже після
парсера, тобто те, що справді пішло б до AI:

| Сторінка | Слів | H | FAQ | Кредитів |
| --- | --- | --- | --- | --- |
| forbes.com/advisor/…/what-is-crm | 3684 | 23 | 5 | 1 |
| trustpilot.com/review/www.amazon.com | 2379 | 25 | 0 | 1 |

```bash
NITRO_FIRECRAWL_TIMEOUT_MS=45000   # необов'язково; ключа тут немає навмисно
```

Терпіння більше за `NITRO_SCRAPER_TIMEOUT_MS` навмисно: влучання в кеш сервісу
приходить за ~1 с, свіжий скрейп — за 5–18 с, а на частині сторінок сервіс
віддає `500 An unexpected error occurred` після 12–36 с. Каскад це не ламає —
5xx стає `http_error`, і наступні ступені працюють як завжди.

**Режим той самий, що в сервісу читання: markdown, а не HTML.** Причина та сама
— у markdown уже немає ні меню, ні банерів, ні скриптів, метадані приходять
окремими полями, а `buildReaderHtml` обгортає результат в `<article>`, тому
парсер довіряє йому напряму й не піднімає JSDOM. Різниця одна: Firecrawl
повертає ще й `metadata.language`, тому атрибут `lang` у складеному документі
не вигаданий, а прочитаний із самої сторінки — як і в ступені 1.

**Дві речі, які виявилися неочевидними й обидві заміряні.**

*Сервіс вважає роботу успішною, навіть коли сайт його не пустив.* На запит
сторінки, якої не існує, приходить `HTTP 200` і `success: true`, а в
`metadata.statusCode` — `403`, а в тексті шість слів «Verifying your
connection…». Тому вихлоп проходить ту саму
[перевірку заслонок](#три-речі-які-виявилися-неочевидними), що й решта ступеней,
і код у неї передається **із метаданих**, а не наш `200`: інакше челендж пішов
би до AI як контент конкурента, ще й обірвавши каскад на ступені, яка нічого не
дала.

*Кеш сервісу спільний для всіх його клієнтів, і він кешує не лише успіхи.*
Заміряно: перший у житті запит на сторінку повернувся з `cacheState: "hit"` і
копією віком 19 годин. Спокуса зробити свіжіше — виставити `maxAge` в годину —
виявилася **гіршою**, і теж заміряно: на trustpilot замість 2599 слів приходить
заслонка на 23. Причина видна в метаданих: ключ кешу враховує режим проксі, тому
годинне вікно не побачило успішної копії, знятої `basic`, піднялося до `stealth`
і влучило в закешовану **невдачу** попередньої такої ж спроби. Тобто коротке
вікно тут не свіжість, а зайвий шанс наступити на власну невдачу.

Тому `maxAge` лишається дефолтом сервісу (**дві доби**), заданим явно — щоб із
коду було видно, що кеш узагалі є. Нуль не годиться і з іншої причини: сервіс
попереджає, що запит без кешу і довший, і частіше падає, а на шостій ступені
бюджет часу вже підточений. Із головною домовленістю каскаду це не конфліктує:
«застаріла копія стоїть останньою й показує дату» — про архів, а його копії
бувають місячної й річної давнини. Стаття конкурента за дві доби — та сама
стаття. На ціну ніщо з цього не впливає: кредит списується однаково, і за
влучання в кеш теж.

Ключ перевіряється при збереженні — запитом `/v2/team/credit-usage`, який
**безкоштовний**, тому перевірка не коштує користувачеві кредиту. Той самий
запит показує залишок на сторінці налаштувань, і навмисно окремим маршрутом, а
не в `/api/me`: профіль читається на кожному екрані, і підмішувати в нього
запит до чужого API означало б платити затримкою за цифру, потрібну на одному
екрані.

### API рендерингу: ступінь 7

Те саме, що ступінь 6, але спільним ключем сервера — для користувачів, які
власного не додавали: чужий браузер із чужої резидентної адреси одним запитом,
тобто і зміна IP, і рендеринг, і обхід челенджу разом.

**Вона стоїть перед ступенем 8, хоч обидві платні, і це заміряно.** На шести
сторінках, закритих [гейтом Turnstile](#гейт-із-turnstile-коли-не-допоможе-жоден-проксі),
цей API узяв **чотири за 5–10 с**, а власний резидентний проксі, Chrome через
нього й читання резидентними адресами сервісу — **жодної**, витрачаючи по 30 с.
Коли API спрацював, за ступінь 8 ми взагалі не платимо.

Провайдер не зашитий: у кожного свій формат адреси, а різниця між ними — лише
порядок параметрів. Тому налаштування — шаблон із підстановками `{url}` і
`{key}`:

```bash
NITRO_SCRAPER_URL=https://api.scraperapi.com/?api_key={key}&url={url}
NITRO_SCRAPER_KEY=…
```

```text
ScrapingBee  https://app.scrapingbee.com/api/v1/?api_key={key}&render_js=true&url={url}
ZenRows      https://api.zenrows.com/v1/?apikey={key}&js_render=true&premium_proxy=true&url={url}
```

**`render=true` у ScraperAPI шкодить, і сильно.** Заміряно на тому самому гейті:
без нього сторінка приходить за 5–10 с і коштує 1 кредит, з ним — `500` після
**56 с** і коштувала б 10. Здоровий глузд каже «челендж потребує рендерингу»,
але сервіс має власний обхід, і режим із рендерингом його вимикає. Тому шаблон
навмисно найдешевший.

Вимога одна: сервіс має віддавати HTML сторінки **тілом відповіді**, а не JSON
із полем — провайдери з JSON-відповіддю тут не працюють. Шаблон без `{url}`
повідомляється як помилка налаштування, а не проковтується: користувач платить
за сервіс, який інакше ніколи не викликався б.

Терпіння тут не «якнайбільше»: успішні відповіді приходять за ≤11 с, а на
невдачі сервіс тягне свої внутрішні повтори ~56 с. Тобто зайвий запас у
`NITRO_SCRAPER_TIMEOUT_MS` не додає успіхів, а лише з'їдає спільний бюджет.

Читання, ліміт розміру, кодування й розпізнавання заслонок беруться ті самі, що
й для прямого запиту — сервіс віддає такий самий HTML, як сам сайт. Помилки
називають хост сервісу: код тут майже завжди про нього (немає кредитів, невірний
ключ, вичерпаний ліміт), а не про сайт, і не назвати його означає звинуватити
чужий хост у чужій проблемі.

### Спільний бюджет часу

Ступеней десять, і сума їхніх таймаутів — понад пʼять хвилин. Тому час у
каскаді спільний: кожна наступна ступінь бере не більше, ніж лишилося, а коли
залишок менший за 3 с — не запускається взагалі (за одну-дві секунди не встигає
навіть рукостискання TLS, і обрізана спроба лише псує повідомлення рядком
«не відповів»).

```bash
NITRO_FETCH_BUDGET_MS=150000   # на Vercel за замовчуванням 120000
```

Різниця для Vercel не про терпіння, а про `maxDuration` функції: сторінки
тягнуться по чотири одночасно, тому одна «хвиля» має влазити в ліміт разом із
відповіддю. Якщо бюджет обірвав каскад, у тексті помилки це сказано окремо —
`далі не пробували — вичерпано час`: така сторінка може взятися з другої спроби,
а звичайне блокування — ні.

### Копія на вимогу

Останню ступінь варто пояснити окремо. Internet Archive має публічний Save Page
Now, і його краулер проходить там, де не проходимо ми. Заміряно на сторінці,
закритій Cloudflare від усіх наших ступенів: копії не існувало, SPN створив її
за 20.6 с — 2615 слів, дата сьогоднішня. Тобто застарілість тут не виникає.

Ступінь остання, бо це безкоштовний публічний сервіс і ~30 с очікування:

```bash
NITRO_ARCHIVE_ON_DEMAND_ENABLED=false   # вимкнути, якщо не потрібна
```

### Три речі, які виявилися неочевидними

**Підробка Chrome-заголовків шкодить.** На вибірці з 8 сайтів успішність упала
з 4/8 до 3/8: zillow.com віддає контент чесному бот-UA і блокує «Chrome».
Причина — TLS-відпечаток Node не відповідає заявленому браузеру, і WAF ловить
саму суперечність. Тому ступінь 1 не вдає браузер, а сайти, для яких потрібен
браузер, беруться справжнім браузером.

**Головний важіль — приховування автоматизації, а не заголовки.** Найбільше
дав `--disable-blink-features=AutomationControlled`, прибирання
`--enable-automation` і підміна UA, який у headless Chrome містить рядок
`HeadlessChrome`. Заміряно: з власним UA reddit віддає 26 слів і rozetka 403,
після заміни — 3949 слів і 200. UA беремо в самого браузера й лише міняємо
`HeadlessChrome` на `Chrome`, щоб рядок не застарів після оновлення Chrome.
Видимий режим переваги над headless не дав.

**Критерій успіху — розібраний текст, а не HTTP 200.** Сторінка-лістинг віддає
код 200 і тисячі слів у картках, а парсер дістає з неї одиниці: reddit — 17
слів, tsn.ua — 1. Тому перевірка придатності стоїть **після** розбору
([MIN_USABLE_WORDS](apps/server/src/services/parser/index.ts)), і якщо тексту
замало — каскад іде далі, а не віддає AI порожнечу. Якщо не допомогла жодна
ступінь, користувач отримує конкретну пораду вказати URL статті, а не лістингу.

**Код відповіді — не вердикт.** Заміряно на trustpilot.com: браузер отримує
`403` **разом із повною сторінкою** — справжній заголовок і 4247 слів тексту.
Стара перевірка бачила код і викидала цей контент, після чого сторінка
діставалася аж копією з архіву. Тепер на будь-якому 4xx/5xx спершу дивимо в
тіло: якщо там повноцінний матеріал без ознак челенджу, беремо його попри код.
Поріг високий (500 слів), бо заслонки бувають балакучі — у Wayback її боілерплейт
важить 583 слова.

**Cloudflare перекладає заслонку.** Ступінь 2 ходить із локаллю `uk-UA`, тому
на glassdoor.com і crunchbase.com приходить не «Just a moment…», а «Трохи
зачекайте…». Розпізнавання заслонок за англійськими рядками на цьому й
спотикалося.

**Очікування має бути умовним, а не фіксованим.** Спершу стояла пауза 4 с після
завантаження. Вона погана з обох боків: сторінки без челенджу чекали марно, а
справжній челендж інколи не встигав. Тепер очікується саме зникнення заслонки
з `<title>`, і це дало прискорення: reddit 4.5 → 2.5 с, rozetka 6.1 → 3.9 с.
Друга така сама пауза стояла після челенджу — «щоб JS домалював контент»;
замість неї браузер чекає, поки обсяг тексту двічі підряд не виявиться
однаковим. Стеля потрібна для нескінченних лічильників і карусельних
заголовків — ті не стабілізуються ніколи.

**`waitForFunction` не тримає власного таймауту.** Найдорожча знайдена
дрібниця. На сторінці з віджетом Turnstile
`page.waitForFunction(…, { timeout: 8000 })` висить рівно **30 с** — стільки,
скільки усталений таймаут Playwright, — і не реагує ні на переданий `timeout`,
ні на `polling: 500`. Тобто задана нами межа очікування просто не діяла, і
кожна заблокована сторінка коштувала 30 с у ступені 2 **і ще 30 с** у ступені 5.
Заміряно покроково: `goto` 0.3 с, `waitForFunction` 30.0 с, `page.title()`
0.0 с, `evaluate` 0.0 с. Тому очікування заслонки — власний цикл на
`page.title()` із паузою власним таймером, а не всередині сторінки:
premiumtimesng 31.7 → **9.0 с**, і `NITRO_BROWSER_SETTLE_MS` тепер справді
керує часом (2.8 с при 2000, 4.9 с при 4000).

**Архів не варто пробувати, якщо сторінку вже отримано.** Коли браузер віддав
повний рендер, а статті в ньому немає, у копії буде та сама сторінка. Без цієї
перевірки лістинг витрачав ~40 с на створення нікому не потрібної копії:
epravda 35.9 → 2.9 с, tsn.ua 46.5 → 6.5 с.

**Кодування треба передавати явно.** Дефолт cheerio — `windows-1252`, тому
італійська сторінка без оголошеного charset читалася як latin1: «velocitÃ&nbsp;»
замість «velocità», «CasinÃ²» замість «Casinò». Такий текст пішов би в промпт і
в готове ТЗ. Тепер charset береться з `Content-Type`, а дефолтом стоїть UTF-8:
у сучасному вебі сторінка без оголошеного кодування майже завжди UTF-8, а
справжній windows-1251 його оголошує — і sniffer це побачить.

### Що перевірено й не працює

Щоб не переробляти це вдруге. Усе заміряно на тій самій вибірці з 8 захищених
сайтів.

| Ідея | Результат |
| --- | --- |
| Повний набір Chrome-заголовків (`sec-ch-ua`, `Sec-Fetch-*`, `Upgrade-Insecure-Requests`) | нуль змін; zillow при цьому 200 → 403 |
| `Referer: google.com` до них | нуль змін |
| User-Agent Googlebot | нуль змін, а reddit 200 → 403 |
| HTTP/2 (`allowH2`) + порядок шифрів і кривих як у Chrome | нуль змін: JA3 усе одно не збігається, бо порядок розширень TLS з Node не задається |
| Безкоштовні CORS-проксі (allorigins, codetabs) | таймаут 19 с і `522` на всіх захищених сайтах |
| Розширений набір патчів проти детекту (`chrome.runtime`, `navigator.plugins`, WebGL-вендор, `permissions.query`) | у межах шуму: zillow 500 → 567 слів, решта без змін |
| Клік по чекбоксу челенджу у фреймі | клікати нічого: у Turnstile на glassdoor і crunchbase нуль елементів, у DataDome на g2 клік по двох знайдених елементах відвалюється таймаутом |

Спільний висновок: усе, що імітує браузер **не будучи** браузером, не працює —
захист дивиться на TLS-відпечаток і поведінку, а не на заголовки. Тому реальні
важелі лише два: справжній браузер (наш або чужий) і справді інша адреса.

### Архівні копії

Контент з архіву може бути застарілим, тому джерело завжди видно в інтерфейсі:
у рядку URL — мітка, у деталях — попередження з датою копії. Дата дістається
з адреси знімка, без додаткового запиту до API.

Окрема пастка: коли копії немає, Wayback віддає власну сторінку-заслонку на
583 слова. Без перевірки цей боілерплейт пішов би до AI як контент конкурента,
тому [archive.ts](apps/server/src/services/fetcher/archive.ts) розпізнає її
окремо, не покладаючись лише на код відповіді.

### Налаштування

```bash
NITRO_FETCH_BUDGET_MS=150000  # стеля часу на весь каскад для однієї сторінки
NITRO_BROWSER_ENABLED=false   # вимкнути ступінь 2
NITRO_BROWSER_PATH=...        # шлях до Chrome, якщо не знайдено автоматично
NITRO_READER_ENABLED=false    # вимкнути ступені 3 і 8
NITRO_READER_KEY=jina_…       # зняти ліміт частоти й відкрити ступінь 8
NITRO_PROXY_URL=...           # увімкнути ступені 4 і 5 (порожньо — вимкнені)
NITRO_FIRECRAWL_TIMEOUT_MS=45000        # терпіння ступеня 6
NITRO_SCRAPER_URL=...         # увімкнути ступінь 7 (шаблон із {url} і {key})
NITRO_SCRAPER_KEY=...
NITRO_ARCHIVE_ENABLED=false   # вимкнути ступінь 9
NITRO_ARCHIVE_ON_DEMAND_ENABLED=false   # вимкнути ступінь 10
```

Ступеня 6 у цьому переліку немає, і це навмисно: вона вмикається не змінною, а
ключем Firecrawl в акаунті користувача — див. [ступінь 6](#firecrawl-ступінь-6).
Тут для неї є лише таймаут.

Браузер не завантажується: використовується вже встановлений Chrome або Edge
(`playwright-core`, без 150 МБ Chromium). Екземпляр один на процес і
закривається хуком у [plugins/shutdown.ts](apps/server/plugins/shutdown.ts) —
інакше після кожного перезапуску dev-сервера лишався б висіти процес Chrome.

Саме тому ступінь 2 не працює в serverless: там немає ні встановленого
браузера, ні довгоживучого процесу, якому належав би його екземпляр. На Vercel
вона вимикається сама — див. [Деплой](#що-на-vercel-працює-інакше).

## AI-шар

Провайдер відділений від бізнес-логіки (розділ 3 ТЗ):

```text
services/ai/          провайдер-агностичний доступ до LLM
  types.ts            інтерфейс AiProvider
  index.ts            providerForUser() — вибір провайдера за ключем
  deadline.ts         стеля часу на запит: щоб обрізали ми, а не платформа
  request.ts          requestJson() — перевірка схеми й одна спроба виправитися
  models.ts           живий перелік моделей від провайдера
  providers/gemini.ts
  providers/openai.ts
  providers/anthropic.ts

services/brief/       бізнес-логіка ТЗ, не знає про конкретного провайдера
  schema.ts           zod-схема SeoBrief
  payload.ts          ParsedPage[] → компактні дані для промпта
  prompts.ts          збірка промптів: підстановка значень і порядок блоків
  generateBrief.ts    оркестрація і нормалізація

services/compare/     порівняння власної сторінки з конкурентами
  metrics.ts          показники, входження ключів і бал — без AI
  schema.ts           дві схеми: запит до моделі й готовий звіт
  prompts.ts          збірка промптів порівняння
  comparePage.ts      оркестрація і склеювання

services/prompts/     тексти промптів, які правляться на сайті
  defaults.ts         початкові тексти — те, до чого повертає скидання
  registry.ts         які промпти є і які вставки в них допустимі
  render.ts           підстановка {{вставок}} і перевірка правки
  repository.ts       prompt_templates: чинний текст, історія, скидання

services/rules/       правила для мов, які дописуються в промпт
  repository.ts       language_rules: перелік для UI і тексти для промпта
```

`services/ai` не знає доменних типів: він приймає JSON Schema й повертає
нерозібраний JSON. `services/brief` не знає, який провайдер працює, — тому
підміна Gemini на OpenAI чи Claude не зачіпає жодного файлу з бізнес-логікою.

`providerForUser()` бере активний ключ користувача з бази — і тільки його.
Немає ключа — 503 із поясненням, а не мовчазний збій посеред генерації.

Особливості адаптерів, які варто знати:

- **Anthropic** — `output_config.format` для строгого JSON і адаптивне
  мислення. Параметри семплінгу (`temperature`) не надсилаються взагалі:
  Opus 5, Opus 4.8 і Sonnet 5 відхиляють їх із 400. Відповідь читається
  стрімом — на 32K токенів звичайний запит встигає впертися в таймаут SDK.
- **OpenAI** — `response_format: json_schema` зі `strict: false`. Строгий
  режим вимагає `additionalProperties: false` і всі поля в `required`, а в
  схемі ТЗ є необовʼязкові; підганяти спільну схему під один провайдер
  означало б зіпсувати її для решти. `temperature` іде лише моделям `gpt-4*`:
  reasoning-моделі його не приймають.

### Формат ТЗ: дві мови в одному документі

ТЗ віддається райтеру, тому в ньому свідомо співіснують дві мови:

| Що | Мова | Приклад |
| --- | --- | --- |
| поля `instruction` | **англійська** | `Write 50-75 words introduction` |
| заголовки, ключі, питання, колонки таблиць, пункти списків | **мова конкурентів** | `Metodi di Pagamento Supportati` |

Мова контенту визначається автоматично
([detect.ts](packages/shared/src/languages/detect.ts)): спочатку з `<html lang>`
проаналізованих сторінок, у резерві — характерні літери в заголовках. В UI
англійські інструкції відокремлені рамкою й мають `lang="en"` — інакше дві мови
в одному блоці легко переплутати.

Функція живе в `shared`, а не на сервері, навмисно: мова показується у вкладці
«Аналіз» і використовується під час генерації, і дві реалізації того самого
голосування розійшлися б — користувач бачив би одну мову, а в промпт ішла б
інша.

Разом із мовою повертаються **підстави**: який шлях спрацював, скільки сторінок
мають придатний `<html lang>`, скільки з них назвали саму цю мову і що казали
решта. Без них «Italian» — число з нізвідки. Резервний шлях саме вгадує:
італійські й французькі діакритики перетинаються, тому сторінка без `lang` може
отримати чужу мову — у вкладці видно, що визначення трималося на здогадці.

Мову **можна виправити вручну** у вкладці «Аналіз». Це не налаштування «якою
мовою писати»: вибір зберігається в сесії як перевизначення (`content_language`,
міграція 0005), тому повторний аналіз його не скидає, а `null` означає звичайне
«вір визначеному». Одне значення діє і на ТЗ, і на аналіз власної сторінки —
мова в сесії одна, і звіт, складений іншою мовою, ніж ТЗ, читався б як чужий.
Раніше мова вперше зʼявлялася в готовому ТЗ, тобто після того, як нею написано
вже все, і виправити її можна було лише перегенерацією.

Визначення повертає пару «код + назва». Назва (`Italian`) іде в промпт і в
поле `contentLanguage`, бо модель розуміє її, а не `it`; код потрібен, щоб
підняти [правила саме цієї мови](#правила-для-мов). Назву в готовому ТЗ
ставить сервер, а не модель: за нею потім шукаються правила для правок
у чаті, і `Brazilian Portuguese` замість `Portuguese` тихо лишило б наступну
правку без правил.

Решта правил формату:

- **Обсяг завжди діапазон**, ніколи точне число: `2550-2950` слів на статтю,
  `250-280` на розділ, `3-5` вживань ключа. Тип [`Range`](packages/shared/src/types/brief.ts).
- **Вступ після H1 — окреме поле `intro`**, а не «нульовий розділ». У реальних
  ТЗ він є завжди й має власні вимоги: кількість абзаців поряд з обсягом,
  тези, які треба розкрити, і ключі. Всередині дерева заголовків він читався б
  як ще один H2, а без окремого поля модель то додавала його як H2, то
  забувала зовсім.
- **Ключі не діляться на типи.** Один плоский список на розділ, і подається він
  нумерованим списком, а не чипами: райтер вичитує його по пунктах.
- **Інструкція обовʼязкова для кожного елемента**: вступу, заголовка, списку,
  таблиці, FAQ. Без неї райтер не знає, що саме туди писати.
- **FAQ без відповідей.** Модель дає лише питання; інструкція задає цільову
  довжину відповіді, а пише її райтер.

Блоки всередині розділу — свідомо плоска структура з полем-дискримінатором
замість обʼєднання типів: структурований вивід моделі надійніше працює
з однорідною схемою, ніж з `anyOf`. Нерелевантні для конкретного `kind` поля
просто лишаються порожніми.

| `kind` | Коли | Що заповнює модель |
| --- | --- | --- |
| `list` | звичайний перелік | `items` |
| `ordered_list` | де порядок несе зміст: рейтинг, топ-N, кроки | `items` |
| `table` | порівняння | `columns`, `rows` |
| `pros_cons` | переваги й недоліки | `prosCount`, `consCount` |
| `questions` | FAQ | `items` (лише питання) |
| `highlight` | один факт, який не можна пропустити | `text` мовою контенту |
| `links` | посилання, які має поставити райтер | `links` (анкор + URL) |
| `template` | десять однотипних описів замість десяти майже однакових H3 | `items`, `itemTemplate`, `itemWordCount`, за потреби `columns`/`rows` і `prosCount`/`consCount` на кожен опис |

### Посилання здебільшого без адреси

У блоці `links` порожній `url` — не пропуск, а звичайний випадок. У референсних
ТЗ із [docs/](docs/) таких блоків 62 на вісім документів, від чотирьох до
дванадцяти на ТЗ, і майже в кожному рядку в колонці URL стоїть `#`: це
внутрішнє перелінкування, і цільову сторінку свого сайту добирає SEO-фахівець,
а не райтер і не модель. Адресу модель заповнює лише для зовнішнього
авторитетного джерела — регулятора, організації допомоги залежним, офіційного
сайту організації, названої в даних конкурентів.

Це не побажання, а те, що модель фізично може знати. Вихідних посилань
конкурентів у [`ParsedPage`](packages/shared/src/types/page.ts) немає — парсер
зберігає текст, заголовки, списки, таблиці й FAQ, але не `href`. Тому «візьми
адресу з даних конкурентів» узагалі неможливо виконати, а будь-який
непорожній `url` — це або справжнє знання моделі про домен, або вигадка.

Розрізняє їх [`normalizeLinkUrl()`](apps/server/src/services/brief/generateBrief.ts):
у ТЗ лишається лише абсолютний `http(s)` URL, а `#`, голий домен і відносний
шлях зводяться до внутрішнього посилання — тобто до того, чим вони й були.
Рядок без анкора викидається: URL сам по собі райтеру нікуди не стає.

### Постійні вимоги до тексту не генеруються

Три блоки в кінці кожного ТЗ — `The most important requirements`,
`Characteristics`, `Important requirements` — у всіх восьми референсних
документах збігаються посимвольно, попри різні мови, теми й обсяги від 2 200 до
11 600 слів. Це бойлерплейт проєкту, а не висновок з конкурентів, тому він не
проходить через модель: платити токенами за незмінний текст і щоразу отримувати
трохи інше формулювання — гірше за обидва варіанти.

Правиться він на сторінці «Промпти», у групі «Текст у самому ТЗ» (ключ
`document.requirements`). Це єдиний текст там, який іде не в модель, і лежить
він серед промптів навмисно: йому потрібно рівно те саме — початковий текст у
коді, правка лише адміном, історія й скидання, — а друга така сама машинерія
заради одного тексту дорожча за одну зайву групу на тій сторінці.

Формат найпростіший із можливих: `#` — заголовок блока, `-` — пункт, `-`
з відступом — уточнення під попереднім пунктом. Нумерація в тексті не
зберігається, а проставляється при показі: інакше вставлений посередині пункт
вимагав би переписати весь блок руками, і рано чи пізно в ньому зʼявилося б
дві сьомих. Розбирає це
[`parseRequirements()`](packages/shared/src/brief/requirements.ts) — пробачливо,
бо текст уже збережений; форму стереже
[`requirementsProblem()`](packages/shared/src/brief/requirements.ts) при
збереженні, через `validate` у реєстрі промптів.

Дійти до інтерфейсу текст може двома шляхами, і вони різні навмисно:

- **робоча сесія** читає чинний текст через `GET /api/brief/requirements` —
  окремим маршрутом, бо вимоги не залежать від сесії, і вкладати кілька
  кілобайт у кожну відповідь генерації нема сенсу. Поки відповідь не прийшла
  (а якщо сервер недоступний — то й зовсім), діє початковий текст із коду:
  спінер на місці блока, який майже ніколи не змінюється, коштував би більше,
  ніж дає;
- **публічне посилання** бере текст зі зліпка. Райтер працює за тим документом,
  який йому дали, і вимога, що змінилася після публікації, зробила б посилання
  не тим, що надсилали. У зліпках, створених до появи поля, його немає — там
  теж діє початковий текст, і саме тому в схемі стоїть `.default()`, а не
  обовʼязкове поле: інакше кожне раніше надіслане посилання відповідало б
  «створено в попередньому форматі».

### Зведена таблиця ключів

Це підсумок **усієї** статті, а не короткий перелік головного: один рядок на
20–40 слів обсягу й не менше 60 рядків. Щільність узята з референсних ТЗ у
[docs/](docs/): у брифі на 6600 слів — 326 ключів (один на 20 слів), у брифі на
7800 слів — 146 (один на 53). Стаття на шість тисяч слів дає 150–300 рядків,
тому це сотні рядків, а не десятки.

`usage` рахує всі входження в готовій статті — у заголовках, таблицях і у складі
довших ключів, — тому в інтерфейсі колонка підписана `Total usage` і має
пояснення під заголовком. Без нього числа виглядають завищеними: райтер рахує
входження лише в абзацах.

Рідкісний ключ отримує точне число, а не діапазон: у референсі 167 рядків із 326
— це `1`, `2` або `3`, і вимагати «діапазон завжди» для одного входження немає
сенсу. Нуль означає протилежне нормі: форма, яку вживати не можна. У референсі
таких 21 рядок — типові для конкурентів варіанти, що не підходять статті. У
таблиці вони внизу й зачеркнуті.

Словоформи — окремі рядки. Для флективних мов це десятки рядків: у шведському
брифі `casino`, `casinon`, `casinot`, `casinots` стоять окремо, і саме вони
займають верх таблиці.

Повноту таблиці не залишено на модель. `normalizeBrief()` збирає ключі зі
вступу, всіх H2 і всіх H3 і **дописує ті, яких у таблиці немає**: ключ, що
видно в розділі й не видно в таблиці, читається як помилка ТЗ і не потрапляє
в жодний підрахунок. Скільки разів ужити ключ, названий у N розділах, —
арифметика, тому дешевше дописати самим, ніж витрачати другий запит до моделі.
Там само знімається суперечність «ключ названий у розділі, але має норму 0».

Там само перевіряється й обсяг: межі впорядковуються, а `totalWordCount`
не може бути меншим за вступ плюс суму розділів.

### Одна схема замість двох

`seoBriefSchema` виконує три роботи одночасно:

1. описує відповідь для моделі — через `z.toJSONSchema()`;
2. валідує те, що модель реально повернула;
3. звіряється з типом `SeoBrief` з `@brief/shared` **під час компіляції**.

Третій пункт — не декорація: якщо додати поле в `SeoBrief` і забути в схемі,
впаде `pnpm typecheck`, а не запит до AI у користувача. Так само зроблено для
`parsedPageSchema` у [schemas/page.ts](apps/server/src/schemas/page.ts).

### Стеля часу: щоб обрізали ми, а не платформа

Схема для моделі — інструкція, а не рейка, і на великому обсязі модель із неї
сходить. Тому [request.ts](apps/server/src/services/ai/request.ts) робить другу
спробу сам, дописавши, де саме сталася розбіжність. На serverless ця спроба
має ціну: **другий повний запит — це приблизно вдвічі більше часу**, а ліміт
тривалості функції нікуди не зникає.

**Заміряно на проді: ТЗ помітно меншого обсягу впало по 504 там, де більше
пройшло.** Обсяг відповіді — не та змінна, що вирішує. Час додають три речі, і
жодна з них не пропорційна розміру ТЗ:

| Що | Чому не залежить від обсягу |
| --- | --- |
| другий запит при розбіжності зі схемою | підкидання монети на кожен запит, а не функція розміру |
| глибина adaptive-мислення | вона про складність і розмитість теми, не про довжину відповіді; `max_tokens` обмежує мислення й текст **разом** |
| повтори SDK на 429 і 529 | той самий запит, той самий розмір, утричі більше часу |

Найгірше в цьому не сам таймаут, а те, що від нього не лишалося слідів. Коли
платформа вбиває функцію, у відповіді немає навіть нашого JSON — тому
[api.ts](apps/web/src/lib/api.ts) не мав що показати, крім шаблонного
«Помилка запиту (504)», а в логах не було ні тривалості, ні причини.

Тому межу тепер тримає [deadline.ts](apps/server/src/services/ai/deadline.ts),
і вона обрізає **раніше** за платформу: `NITRO_AI_BUDGET_MS`, на Vercel 280 с
при `maxDuration` 300. Три наслідки:

- обрив за часом стає `ai_timeout` 504 **з тілом** — користувач бачить причину
  й пораду, а не код;
- друга спроба **не починається**, якщо на неї вже не лишилося часу: краще
  сказати правду одразу, ніж бути вбитим на півдорозі (перевірено — у цьому
  разі виклик до моделі рівно один);
- тривалість і витрату токенів кожної спроби видно в логах завжди, а не лише
  на помилці.

**Механізм — сигнал розриву, а не опція `timeout` клієнта SDK,** і це важливо:
таймаут SDK **повторюється** (`maxRetries` за замовчуванням 2), тому реальний
час доходить до `timeout × 3` і межа перестає бути межею. Обрив користувачем
SDK не повторює ніколи — тому один сигнал обмежує загальний час незалежно від
того, скільки повторів устигло статися всередині. `maxRetries` при цьому
лишається типовим: він корисний проти 429 і 529, а загальний час усе одно
обмежений.

Скасування користувачем і вичерпаний бюджет для провайдера виглядають однаково
(сигнал один), і розрізняються лише в `request.ts` — інакше «Запит скасовано»
показувалося б там, де користувач нічого не натискав.

Якщо 280 с замало, піднімати треба **разом** із `maxDuration`: стеля, більша за
ліміт функції, не працює — платформа однаково вбиває раніше. А на Hobby вище за
300 с не піднімається взагалі — це максимум тарифу; Pro дозволяє 800 с,
а поштучно (beta) — до 1800.

Було 50 с при `maxDuration` 60, і в них закономірно не вкладалася правка
в чаті: вона повертає **повне оновлене ТЗ**
([chatSchema.ts](apps/server/src/services/brief/chatSchema.ts)), тобто коштує
стільки ж, як генерація, а з другим запитом при розбіжності зі схемою —
удвічі більше.

### Вибір моделі

Набір доступних моделей залежить від ключа, тарифу й регіону, тому список
у налаштуваннях **завжди береться з живого API провайдера**
([services/ai/models.ts](apps/server/src/services/ai/models.ts)), а не з
власного переліку. Цей самий виклик слугує перевіркою ключа: неробочий ключ
відхиляється одразу, а не через хвилину очікування першого ТЗ.

Каталог у [packages/shared/src/ai/catalog.ts](packages/shared/src/ai/catalog.ts)
додає до живого списку лише ціни й мітки (`Рекомендована`, `Збалансована`,
`Дешевша`, `Преміум`). Модель, якої в каталозі немає, все одно зʼявиться
у виборі — просто без бейджа й ціни.

Ціни там, де їх не вдалося підтвердити, лишені порожніми навмисно:
показати «приблизно» гірше, ніж не показати нічого — на цифру з інтерфейсу
планують бюджет. Для Anthropic у каталозі лише моделі з підтримкою
structured outputs: бриф приходить строгим JSON за схемою, і модель без
цієї можливості з ним не впорається.

Заміряно на одному й тому самому запиті (3 сторінки конкурентів):

| Модель | Час | Якість ТЗ |
| --- | --- | --- |
| `gemini-3.6-flash` | 20.5 с | порівнянна, типова |
| `gemini-2.5-pro` | 43.3 с | порівнянна |

### Чат: правки ТЗ

`POST /api/chat` доопрацьовує наявне ТЗ за текстовим запитом. Повторного
парсингу URL не відбувається (розділ 10 ТЗ).

Схема відповіді має дискримінатор `action`, яким модель сама повідомляє, чи
були правки:

| action | Що повертається | Навіщо |
| --- | --- | --- |
| `answer` | лише `reply` | На питання «чому такий обсяг?» переписувати все ТЗ і зайво, і ризиковано |
| `edit` | `reply` + повне оновлене ТЗ | Правку застосовано |

Заміряна різниця: питання — 4.3 с, правка — 11–15 с. Звʼязок «`edit` ⇒ `brief`
присутній» перевіряється в коді, а не схемою: `anyOf` у `responseJsonSchema`
підтримують не всі провайдери.

У чат ідуть **не всі** дані конкурентів, а скорочені — тільки структура
заголовків, обсяг і питання FAQ
([buildCompactPagesPayload](apps/server/src/services/brief/payload.ts)).
Повний контент для правок не потрібен, а чат викликається багато разів.

`temperature` для правок — 0.2 замість 0.4: правка має бути точною, не творчою.

У чат іде те ТЗ, яке зараз на екрані, — разом із ручними правками. Тому вони
не втрачаються: модель бачить їх як частину ТЗ і повертає у своїй відповіді.
Ця відповідь стає новою машинною версією — див.
[Ручна правка ТЗ](#ручна-правка-тз).

## Ручна правка ТЗ

Згенероване ТЗ редагується на місці: клік у будь-яке значення — і воно
правиться там, де стояло. Модель дає чернетку, останнє слово лишається за
людиною, і для цього не потрібно ні окремого режиму, ні кнопки «Редагувати».

Правиться все, крім типу блоку:

| Що | Приклади |
| --- | --- |
| Текст | Title, Meta Description, H1, заголовки H2–H4, інструкції англійською, тези вступу, пункти списків, анкори й адреси, ключі, назви колонок і підписи рядків, поради |
| Цифри | обсяг статті, розділу, підрозділу, H4 і вступу, кількість абзаців, вживання ключа, скільки переваг і недоліків, обсяг одного опису |
| Структура | додати, видалити й переставити розділ, підрозділ, H4, блок, пункт, колонку, рядок, посилання, ключ, доповнення, пораду |

Тип наявного блоку не змінюється навмисно: список і таблиця тримають дані в
різних полях, і перемикання типу означало б або втратити набране, або лишити
в блоці поля, яких у ньому не має бути. Потрібен інший тип — блок додається
заново, а старий видаляється.

### Чому contenteditable, а не поля введення

Це не питання смаку. Копіювання ТЗ у документ збирає розмітку самої панелі
([copySelection.ts](apps/web/src/lib/copySelection.ts)), і поля введення воно
пропускає навмисно — разом із кнопками, службовими лічильниками й нумерацією
карток. Тобто з `input` кожне редаговане значення **зникло б із того, що
райтер вставляє в Google Docs**.

Елемент із `contenteditable` лишається звичайним елементом із текстом, тому ні
збирач документа, ні верстка не помічають, що поле стало редагованим. Із цього
ж випливає решта рішень:

- **кнопки правки** — переставити, видалити, повернути машинне значення — не
  потребують жодних винятків: `BUTTON` і `SELECT` збирач документа пропускає
  сам;
- **підказка в порожньому полі** зроблена через `::before`, а не вкладеним
  елементом: збирач читає текстові вузли, а згенерованого вмісту в DOM немає —
  тому «назва розділу» не поїде в документ;
- **порядок таблиці ключів** у правці — той, що в ТЗ, а не відсортований за
  вживаннями: сортування переставляло б рядок під руками, щойно виправили
  число. У документ таблиця все одно йде відсортованою — його збирає
  [briefDocument.ts](apps/web/src/lib/briefDocument.ts) із даних, а не з
  розмітки.

Текст під час набору живе в DOM, а не в стані React
([InlineEditable.tsx](apps/web/src/components/brief/edit/InlineEditable.tsx)):
перемальовка з новим значенням зсувала б каретку в початок рядка на кожній
літері, а перемальовок тут вистачає — ТЗ зберігається саме, і поряд
оновлюються і позначки, і сума обсягів. Межа проста: у фокусі правду знає DOM,
поза фокусом — React.

### Правка адресується шляхом, а не полем

ТЗ — дерево на чотири рівні заглиблення, тому кожна правка описується шляхом:
`["structure", 3, "children", 1, "title"]`
([briefEdit.ts](apps/web/src/lib/briefEdit.ts)). Компонент, що малює заголовок
H3, знає свій шлях і не знає більше нічого — ні про сесію, ні про збереження.
Заміна копіює лише гілку від кореня до поля; решта дерева лишається тими
самими об'єктами.

Правка приходить **функцією** від попереднього ТЗ, а не готовим значенням:
поля зберігаються самі, і дві правки можуть статися до наступної
перемальовки — готове значення в такому разі рахувалося б від застарілого ТЗ
і перетирало б сусідню правку.

Діапазони правляться текстом — «100-150», — а не двома полями чисел: у ТЗ це
один показник, і два поля зі стрілками розбили б рядок «заголовок · обсяг ·
копіювати», який тримає всю панель. Нерозпізнане просто не зберігається, і в
полі знову з'являється попереднє значення: «100-» на півдорозі до «100-150» —
не помилка користувача, а нормальний проміжний стан, і повідомляти про неї
нема про що.

### Дві версії ТЗ

У сесії лежать обидві: `brief` — робоча, `original_brief` — та, яку віддала
модель (міграція
[0010](supabase/migrations/0010_brief_edits.sql)). Різниця між ними не
історія, а робочий інструмент: саме вона відповідає на «що тут моє, а що
написала модель».

| Дія | `brief` | `original_brief` |
| --- | --- | --- |
| Генерація ТЗ | нове | те саме нове |
| Правка з чату | відповідь моделі | те саме |
| Ручна правка | змінене поле | **не змінюється** |

Оригінал рухає лише модель — і чат теж: він отримує вже відредаговану версію
й повертає її разом зі своїми змінами, тому його відповідь — така сама машинна
версія, а не привід позначити чужу роботу як ручну.

Позначкою «змінено вручну» служить сама поява кнопки повернення поряд із
полем: окремий значок при ній читався б як другий, інший стан. Кнопка
повертає машинне значення одного поля; «Повернути згенероване» вгорі —
все ТЗ, і показується лише коли ручні правки взагалі є.

Сесія, ТЗ якої зберегла версія до `0010`, лишається без оригіналу — і тоді
немає ні позначок, ні повернення. Виправляє це перша ж правка: разом із нею
клієнт надсилає те, що було до неї, а сервер записує це в порожню колонку
(і лише в порожню — у другій вкладці правка могла статися раніше, і її
оригінал правильніший).

### Збереження

Окремим маршрутом `PUT /api/sessions/:id/brief`, а не `PATCH` сесії, і причина
не в чистоті: `PATCH` віддає у відповіді всю сесію разом із розібраними
сторінками — сотні кілобайт на кожну паузу в наборі. Тут у відповіді лише час
запису, який панель показує позначкою «збережено».

Пауза до запису — 400 мс, і вона склеює правки в сусідніх полях, а не сам
набір: готовий текст поле віддає й так через паузу в наборі. Незаписана правка
не пропадає ні при переході на іншу сесію, ні коли вкладку згорнули
(`visibilitychange`, а не `beforeunload`: на мобільних браузерах останній при
перемиканні застосунку не настає взагалі).

Записане ТЗ звіряється тією ж схемою, якою перевіряли відповідь моделі
([brief/schema.ts](apps/server/src/services/brief/schema.ts)): правка додає
порожні поля й прибирає розділи, і ТЗ після неї має лишитися тим самим
документом, а не «майже ТЗ». Помилка запису стан не відкочує — набраний текст
у користувача перед очима, і прибрати його через невдалий запис було б гірше
за саму невдачу; наступна правка спробує записати ще раз.

Правка піднімає `updated_at` сесії тим самим тригером, що й будь-яка інша
зміна, — тому опублікована версія після неї стає відсталою, і це видно
в панелі публікації.

### Публічне посилання правки не отримує

ТЗ за посиланням малюють ті самі компоненти, що й у робочій сесії. Різницю
робить контекст правки
([BriefEditContext.tsx](apps/web/src/components/brief/edit/BriefEditContext.tsx)):
за замовчуванням правка **вимкнена**, а всі операції в ньому пусті. Щоб поля
стали редагованими, потрібно поставити провайдер і дати йому обробник — тобто
випадково це ввімкнутися не може, а публічна сторінка не має про правку знати
взагалі.

## Аналіз власної сторінки

Другий сценарій сервісу (розділ 15 ТЗ): у сесії є не лише конкуренти, а й
**власна сторінка** — та, що вже існує й має з ними конкурувати. `POST /api/compare`
відповідає на питання «чого на ній бракує з того, що покривають конкуренти».

Вкладка «Моя сторінка» стоїть останньою навмисно: ТЗ і чат — одна пара
(«склади» і «поправ»), і вклинювати між ними окремий сценарій означало б
розірвати її.

### Адреса задається при створенні сесії

У формі нової сесії власна сторінка — окреме необовʼязкове поле поряд із
переліком конкурентів. Без нього найчастіший сценарій («у мене вже є стаття,
чого їй бракує?») вимагав би створити сесію, дочекатися аналізу й лише тоді
згадати про власну адресу в іншій вкладці.

Окреме поле, а не ще один рядок серед конкурентів: сторінка й не конкурент, і
в промпт ТЗ не йде. Одним списком вона тихо потрапила б у бриф, який має її
виправити.

Вставляється вона **тим самим запитом**, що й конкуренти: окремий запит міг би
не пройти, і сесія лишилася б без сторінки — при тому, що адресу користувач
уже вказав, і повторити цей крок йому нема де.

Заповнене з помилкою поле — це помилка, а не «пусто»: мовчки відкинути введену
адресу гірше, ніж попросити її виправити.

### Один вхід у парсинг

Власну сторінку можна задати двома шляхами — при створенні сесії й формою у
вкладці, — але **запускає її парсинг лише одне місце**: автозапуск
у [SessionPage](apps/web/src/pages/SessionPage.tsx), який бачить статус
`pending`. Форма нічого не парсить сама, вона лише зберігає адресу.

Два входи означали б два запити на ту саму адресу в момент, коли форма й
автозапуск спрацювали разом. Ключ автозапуску — id сторінки, а не прапорець
«уже стартували»: заміна адреси має запустити парсинг знову, а та сама
сторінка — ні.

### Що рахує сервер, а що вирішує модель

Головне рішення цієї частини — межа між ними:

| Рахує сервер | Вирішує модель |
| --- | --- |
| обсяг, H2, H3, абзаци, списки, таблиці, FAQ — своє проти медіани й максимуму | які теми конкурентів узагалі є темами |
| скільком конкурентам належить ключ і скільки разів він є в нас | які ключі варті уваги |
| нинішні Title, Description, H1 | чим їх замінити й чи варто |
| підсумковий бал і три його складники | вирок, план дій, сильні сторони |

Причина та сама, з якої `normalizeBrief()` сам дораховує таблицю ключів:
«скільки разів слово трапляється в тексті» — пошук підрядка. Модель відповіла б
на око, витратила б на це токени й на повторному запуску дала б інші числа.
Тому [схема запиту до моделі](apps/server/src/services/compare/schema.ts) цих
полів **не містить узагалі**: поле, яке модель може заповнити приблизно, вона
заповнить приблизно.

Побічна вигода: входження ключів рахуються по **повному** `ParsedPage`, а не по
скороченому payload, який бачила модель. Ключ у тридцять п'ятому абзаці, що не
влучив у промпт, лишається знайденим.

### Бал і його ваги

```text
total = 0.5 × структура + 0.3 × обсяг + 0.2 × ключі

структура   розкриті розділи конкурентів; слабкі — за половину
обсяг       свій обсяг / медіана конкурентів, стеля 100
ключі       частка ключів конкурентів, які на сторінці вже є
```

Три складники показуються поряд із загальним балом разом із вагами: саме
число без розкладу — чорна скринька, довіряти якій немає підстав. Ваги живуть
у коді, а не задаються моделлю, — інакше два запуски на тих самих даних дали б
різні бали.

Дві межі неочевидні, але важливі:

- **Понад медіану обсяг не додає балів.** Довша за конкурентів сторінка не
  «краща за 100%»: обсяг сам по собі не мета, а вийти за межі шкали означало б
  компенсувати ним прогалини в структурі.
- **Порожній набір — це 100, а не 0.** Сторінка, для якої модель не назвала
  жодного розділу чи ключа, нічого не провалила, і нуль тут був би покаранням
  за брак даних, а не оцінкою.

### Що ще перевіряється в коді

Те, що модель інколи псує, а перевірити дешево:

- кількість конкурентів у розділі обрізається до їхнього реального числа;
- обсяг для розділу зі статусом «розкрито» відкидається — дописувати там нічого;
- межі діапазонів упорядковуються (`normalizeRange`);
- на кожне поле метаданих лишається один запис, і перший, а не останній: дубль
  від моделі — це та сама порада, переказана вдруге;
- пропозиція, що дослівно повторює наявне значення, стає «лишити як є».

Склеєний звіт наостанок звіряється з тією ж схемою, якою потім читається
з бази, — як і ТЗ.

### Чому наявне ТЗ у порівняння не передається

Спокуса очевидна: якщо ТЗ уже є, можна порівнювати сторінку з ним. Але тоді
звіт має дві різні форми залежно від того, чи ТЗ згенеровано, і читається як
два різні звіти. Вимога ТЗ — «відносно конкурентів», і порівняння працює
незалежно від того, чи існує бриф.

Правила для мов, навпаки, дописуються: модель пропонує тут заголовки, ключі й
новий Title тією ж мовою й для того ж проєкту, і порада, яка ламає чинну
вимогу, гірша за відсутність поради.

### Як вона зберігається

Власна сторінка проходить рівно той самий шлях, що й конкуренти: той самий
каскад доступу, той самий парсер, той самий `ParsedPage` — і той самий
`PATCH /api/sessions/:id/analyses/:analysisId` для збереження результату. Тому
вона лежить у `session_analyses`, а не в окремій таблиці, і відрізняє її одна
колонка `role`.

Один наслідок каскаду тут варто мати на увазі: якщо власний сайт закритий від
автоматичного доступу, сторінка може прийти **з архіву** — і тоді звіт
стосується копії, а не поточного тексту. Мітка джерела й дата копії видні
в рядку сторінки й у деталях так само, як для конкурентів, тому це помітно;
але це саме той випадок, коли на мітку варто дивитися.

Без цієї колонки вона мовчки пішла б у промпт генерації ТЗ разом із
конкурентами — і ТЗ склалося б у тому числі зі сторінки, яку воно має
виправити. Тому в самій сесії це окреме поле `ownPage`, а не ще один рядок
у `analyses`.

Власна сторінка в сесії одна, і це тримає частковий унікальний індекс, а не
лише код: без нього обірваний запит на заміну лишив би дві «власні» сторінки,
і яка з них справжня, не сказав би ніхто.

Заміна адреси скидає звіт: він прив'язаний до конкретного URL, і залишити
старий звіт біля нової сторінки означало б показувати вирок над чужим текстом.
Результати парсингу конкурентів при цьому не чіпаються — повторне порівняння
не завантажує їх заново.

Звіт, записаний попередньою версією формату, прибирається так само, як
застаріле ТЗ, але без прапорця й повідомлення: ТЗ — головний результат сесії, і
його зникнення треба пояснити, а порівняння відтворюється однією кнопкою.

### Застарілий звіт видно

Якщо конкурентів проаналізували заново вже після порівняння, звіт складено за
даними, яких у сесії більше немає. Панель показує це попередженням: мовчки
показувати вирок за старими даними гірше, ніж попросити натиснути кнопку ще
раз.

## Правила для мов

Правило — додаткова вимога до ТЗ. Чинні правила дописуються в промпт кожного
разу, коли генерується ТЗ, — і в генерацію (`/api/brief`), і в правки через чат
(`/api/chat`). У чат вони йдуть теж, і це не дублювання: правка, яка ламає
вимогу, якій ТЗ відповідало до неї, гірша за відсутність правки.

### Дві області дії

| `language_code` | Коли діє | Приклад |
| --- | --- | --- |
| код ISO 639-1 (`it`) | мова конкурентів збігається | «звертатися до читача на *tu*, не на *Lei*» |
| `*` | завжди | «у заголовках H2 не ставити крапку в кінці» |

Спільна область потрібна саме через перелік мов: правило «не ставити крапку
в кінці H2» від мови не залежить, і писати його 183 рази — не варіант.
Сентинелом узято `"*"`, а не `"all"`: три літери можуть колись стати кодом
мови, а зірка — ні.

У промпті це два підписані блоки, а не злитий перелік, і промпт прямо каже,
що при суперечці виграє вужче правило: спільне писали, не думаючи про
італійську, а італійське — думаючи. `activeRules()` віддає обидва набори
одним запитом (`in ('*', 'it')`) — два послідовних дали б ту саму відповідь
удвічі довше.

### Перелік мов — увесь ISO 639-1

[registry.ts](packages/shared/src/languages/registry.ts) — 183 коди, а не
«мови, які ми бачили». Обрізаний перелік означав би, що для грузинських
конкурентів правило додати неможливо, доки хтось не допише код у файл.
Реєстр живе в коді, бо статичний і потрібен обом сторонам: сервер визначає
ним мову зі `<html lang>`, фронт малює з нього список вибору.

Вибір — комбобокс із пошуком
([Combobox](apps/web/src/components/ui/Combobox.tsx)), а не `<select>`: у
нативного списку з 183 рядків знайти шведську можна лише прокруткою або набором
точної англійської назви. Пошук іде за англійською назвою, самоназвою і кодом —
`svenska`, `Swedish` і `sv` ведуть в одне місце. «Усі мови» стоять першими й
відділені лінією, далі мови, для яких правила вже є (з кількістю), далі решта:
працюють щодня з двома-трьома.

Той самий компонент обслуговує ще два місця: мову контенту у вкладці «Аналіз» і
вибір моделі в налаштуваннях. У моделей та сама проблема, що й у мов, — назви
починаються однаково (`Gemini 2.5 Flash Lite`, `Gemini 2.0 Flash`), і в
нативному списку їх доводиться перечитувати очима, тоді як пошук по `lite` або
`3.6` дає одну відповідь. Групи за призначенням («Рекомендована», «Дешевша»)
лишилися — вони кажуть, що взяти, коли байдуже. Три копії клавіатурної навігації,
закриття по кліку поза списком і `aria` розійшлися б у поведінці, тому
варіативність винесена в дані опції, а не в пропси-прапорці.

### Дві ролі

| Роль | Може |
| --- | --- |
| `user` | бачити чинні правила, пропонувати нові, бачити вирок над своїми пропозиціями |
| `admin` | усе те саме + розглядати чужі пропозиції (з причиною відхилення), писати одразу чинні правила, **правити текст**, вмикати, вимикати й видаляти |

Правка й відхилення розкриваються на місці, а не в модальному вікні: обидві
дії роблять, дивлячись на сусідні правила, і затуляти їх діалогом означає
забирати саме той контекст, у якому вирішують. `Ctrl/Cmd+Enter` зберігає,
`Esc` скасовує.

Роль лежить у `profiles.role` і керує **лише правилами**: сесії, ключі й
генерація ТЗ від неї не залежать.

Першого адміна нема кому призначити з інтерфейсу, тому є `NITRO_ADMIN_EMAILS` —
пошти через кому. Акаунт із такою поштою отримує роль при першому ж читанні
профілю. Підвищення тільки в один бік: прибрана з `.env` пошта прав не знімає,
бо адміна могли призначити вручну в базі, і `.env` не має цього скасовувати.
Знімається роль там само, де й видавалася вручну:

```sql
update public.profiles set role = 'admin' where email = 'you@example.com';
```

`requireAdmin` ([http/admin.ts](apps/server/src/http/admin.ts)) — окремий
middleware, а не перевірка всередині `requireAuth`: роль лежить у базі, і
читати її на кожен запит до `/api/analyze` чи `/api/sessions` означало б
додати їм зайвий похід у Postgres.

### Статус і вмикання — різні поля

```text
status   pending → approved | rejected     вирок пропозиції
enabled  true | false                      чи діє схвалене правило зараз
```

Одним полем це не описати: «вимкнути на тиждень» і «відхилити назавжди» —
різні дії, і зводити їх до одного стану означало б втрачати різницю між
«поки не треба» і «так не робимо». Схвалення автоматично вмикає правило —
інакше «прийняти» нічого не змінювало б для того, хто вимкнув його раніше, —
і знімає причину відхилення: «діє» поряд з «не годиться» суперечливий стан,
а не історія.

Відхилене правило адмін може прийняти все ж: відхилення могло бути помилкою,
а переписувати текст заново — марна праця.

Позначки «змінено» в картці немає навмисно: `updated_at` рухає будь-яка дія
адміна, зокрема вмикання, тому за ним не видно, чи правили саме текст.

### Чому пропозиції, а не вільний ввід

Текст правила потрапляє **в промпт до моделі**. Рядок, якого ніхто не читав,
там опинятися не має, тому правило від звичайного користувача діє лише після
схвалення. У самому промпті блок правил ще й огороджений як дані, а не
інструкції ([prompts.ts](apps/server/src/services/brief/prompts.ts)), і стоїть
останнім: правило має перебивати спільні настанови, а не тонути серед них.

Межі теж не косметичні: 500 символів на правило й 40 чинних правил на мову.
Довший перелік витісняє з промпта самі дані конкурентів — а саме вони і є
предметом аналізу.

Дублі відсіюються до вставки, без огляду на регістр: те саме правило, подане
вдруге, дає адміну ще один рядок у черзі й нічого більше.

### Що куди йде

```text
services/rules/repository.ts   доступ до language_rules
  listRules()                  для інтерфейсу: зі статусом, автором, «моє»
  activeRules()                для промпта: тексти чинних правил, '*' і мови
  languageRuleStats()          дублі й межа перед вставкою
```

Розділення не косметичне. `activeRules()` фільтрує в базі, а не в коді —
пропозиція, що чекає розгляду, не має жодного шансу дійти до моделі.

`languageRuleStats()` теж не читає через `listRules()`: той фільтрує за
видимістю, і перевірка на дубль побачила б лише частину даних — користувач
створив би копію чужої пропозиції, якої йому не показують, і дізнався б про
це вже від адміна.

Правила підтягуються **всередині** `generateBrief()`, і передаються туди
функцією, а не готовим списком: мова визначається зі самих сторінок, тому на
момент виклику ще не відомо, правила якої мови потрібні. Так файл із
бізнес-логікою лишається без жодного знання про базу — рівно як і
з AI-провайдером.

Помилка читання правил не зриває генерацію: краще ТЗ без правил, ніж порожній
екран замість ТЗ після хвилини очікування.

### RLS

`language_rules` закрита політиками того ж рівня, що й решта схеми: читати
чинні правила може будь-хто, свої пропозиції — автор, усе інше — адмін;
правити й видаляти — тільки адмін. Перевірка ролі — через
`security definer`-функцію `is_admin()`: `profiles` закрита політикою «лише
свій рядок», і без цього підзапит не побачив би навіть власний профіль.

Разом із роллю в `profiles` з'явилося те, чого там не було, — привілей. Тому
`0003` знімає з `authenticated` і `anon` право писати в `profiles`: політика
`profiles_self` із `0001` дозволяє власнику будь-яку дію зі своїм рядком, RLS
не вміє обмежувати окремі колонки, і без цього будь-хто підняв би собі права
одним `UPDATE` через publishable-ключ. Застосунок у `profiles` з браузера не
пише — усі зміни йдуть через `/api` сервісним ключем.

## Промпти

Текст завдання для моделі правиться на сторінці **Промпти** — тим самим
принципом, що й правила для мов: користувач бачить, адмін змінює. Причина
проста: формулювання промпта — робота SEO-фахівця, і вимагати на кожне його
слово розгортання проєкту абсурдно.

Промптів вісім, і межа проведена там, де вони й були функціями в коді:

| Ключ | Де працює |
| --- | --- |
| `brief.system` | завдання моделі при генерації ТЗ |
| `brief.user` | тема й розібраний контент конкурентів |
| `chat.system` | правки готового ТЗ через чат |
| `compare.system` | аналіз власної сторінки проти конкурентів |
| `compare.user` | дані власної сторінки й конкурентів |
| `compare.language_split` | межа двох мов у звіті порівняння |
| `shared.rules` | спільні правила ТЗ — і в генерацію, і в чат |
| `shared.team_rules` | обгортка, якою правила для мов подаються моделі |

### Початковий текст живе в коді

У базі зберігаються **лише правки**: рядок у `prompt_templates` є — діє його
текст, рядка немає — діє текст із
[defaults.ts](apps/server/src/services/prompts/defaults.ts). Через це:

- «скинути до початкового» завжди має що відновити, у якому б стані не була
  база й скільки б правок не накопичилося;
- на новому проєкті промпти працюють одразу, без «засівання» таблиці;
- скидання — це `delete` рядка, а не пошук найпершої редакції в історії.

Історія — окрема таблиця, лише з дописуванням. Чинний текст читається на
**кожну** генерацію, і тягнути через цей запит усі попередні редакції означало
б платити за історію в найгарячішому місці. Редакція зберігається повним
текстом, а не різницею: її читають очима, і повернути будь-яку можна одним
запитом — та сама дія, що й правка руками, тому повернення теж лишається
в історії.

### Вставки — єдиний машинний запобіжник

Промпт не проходить розгляду, як правило для мови: адмін пише текст, і він
одразу йде в модель. Тому те, що можна перевірити машинно, перевіряється
до збереження ([render.ts](apps/server/src/services/prompts/render.ts)):

```text
{{pagesJSON}}   → відхилено: у цьому промпті такої вставки немає
без {{pagesJson}} → відхилено: обовʼязкова
без {{teamRules}} → відхилено: правила для мов перестали б діяти тихо
```

Опис вставок лежить у
[registry.ts](apps/server/src/services/prompts/registry.ts) поряд із
підстановкою — розійтися вони не можуть, і той самий перелік приходить
у браузер. Обовʼязкові позначені зірочкою й акцентом: без `{{pagesJson}}`
промпт генерації попросив би модель придумати ТЗ із нічого.

Реєстр звіряється сам із собою при завантаженні модуля. Пастка, яку це
ловить, неочевидна: змінна позначена обовʼязковою, але в початковому тексті
її немає — і тоді **будь-яка** правка цього промпта відхиляється вимогою
повернути вставку, якої там ніколи не було. Саме так і сталося з
`{{languageUpper}}` у `brief.system`: мовний поділ у ньому живе не сам,
а всередині `{{sharedRules}}`.

Чого перевірка не робить — не судить сам текст. Промпт, який просить дурницю
осмисленою англійською, це ризик, який лишається за адміном; рівно для нього
поряд є історія й кнопка скидання.

### Що лишилося в коді

Не все, що складає промпт, є текстом. У
[brief/prompts.ts](apps/server/src/services/brief/prompts.ts) лишилася
збірка — те, чого в полі введення не напишеш:

- нумерація правил поспіль через два блоки, щоб не було двох «1.»;
- порожній блок замість заголовка «TEAM RULES» без жодного правила під ним —
  інакше модель читає його як вимогу правила вигадати;
- речення про те, що при суперечці виграє правило мови, — лише коли діють
  обидва набори;
- відступ, яким блок правил приклеюється до промпта: порожні рядки на початку
  поля введення виглядають випадковими, і перше, що з ними зробить редактор, —
  приберуть.

Промпти передаються в `generateBrief()` готовим набором, а не функцією як
правила: вони не залежать ні від мови, ні від чогось іншого, що стає відомим
уже всередині. Помилка читання не зриває генерацію — краще ТЗ за початковими
промптами, ніж порожній екран замість ТЗ.

### Права

| Роль | Може |
| --- | --- |
| `user` | бачити текст усіх промптів повністю |
| `admin` | + правити, скидати до початкового, дивитися історію й повертати редакції |

Пропозицій, як у правил, тут немає навмисно. Правило додається до переліку й
може почекати розгляду, нічого не ламаючи. Промпт існує в єдиному екземплярі:
«пропозиція нового тексту завдання для моделі» — це або новий текст, або
нічого, і проміжного стану в неї бути не може.

Історію бачить лише адмін: сам текст промпта потрібен кожному, а хто і коли
його правив — службова інформація, яка на ТЗ не впливає.

Бізнес-логіка відділена від UI (розділ 14 ТЗ): `services/*` не імпортують

напряму — тільки через [lib/api.ts](apps/web/src/lib/api.ts) і
[lib/storage.ts](apps/web/src/lib/storage.ts).

### Каркас інтерфейсу

Двоколонковий, як у ChatGPT, Gemini і Claude: список сесій зліва, робоча
область справа. Сесії згруповані за давністю (Сьогодні / Вчора / Останні
7 днів / Раніше) — у роботі їх накопичуються десятки, і «сьогодні» треба
відрізняти від «місяць тому» без читання дат.

На екранах вужчих за `lg` панель стає шухлядою: 17rem від 360px не лишають
місця під сам вміст. Останні пʼять сесій дублюються на головній — інакше на
телефоні відкрити недавню сесію можна лише через два натискання.

### Як зберігаються сесії

У Supabase, по одному рядку на сесію плюс окремі таблиці для спарсених
сторінок і повідомлень чату. Розкладка навмисно дрібна: одна сторінка важить
сотні кілобайт, і переписувати весь набір щоразу, коли завершився один URL,
означало б слати мегабайти на кожну дію. Список у бічній панелі читає
обчислювану колонку `has_brief` замість самого JSON з ТЗ.

ТЗ у рядку сесії лежить двома копіями — робочою й машинною
(`brief` і `original_brief`): різниця між ними й є позначками ручних правок,
див. [Ручна правка ТЗ](#ручна-правка-тз).

Доступ подвійний: сервер ходить у базу сервісним ключем і сам звіряє
`user_id` з перевіреного JWT, а RLS у схемі — другий рубіж на випадок, якщо
до бази колись піде фронт напряму.

Активна вкладка сесії живе в `sessionStorage` — це стан перегляду, а не дані,
і він має зникати разом із вкладкою браузера.

Опублікована версія сесії — окремий рядок у `session_shares` із замерзлим
зліпком, а не прапорець «публічна» на самій сесії: див.
[Публічне посилання](#публічне-посилання).

### Авторизація

Supabase Auth, пошта й пароль. Фронт отримує токен, бекенд перевіряє його
локально за JWKS проєкту ([http/auth.ts](apps/server/src/http/auth.ts)) —
без мережевого запиту на кожен виклик API. Запасний шлях, звернення до
`/auth/v1/user`, потрібен для старих проєктів Supabase із симетричним HS256:
у них JWKS порожній.

`requireAuth` підключається **всередині кожного роутера**, а не одним рядком
у `app.ts`: так неможливо додати маршрут і забути про захист. Без входу
доступні лише `/api/health` і `/api/public/*` — останнє зібране в один роутер
із тієї самої причини, тільки з іншого боку: доступність усім видно з файлу
(див. [Публічне посилання](#публічне-посилання)).

Парсинг (`/api/analyze`) закритий теж, хоча AI там не задіяний: він ходить
у зовнішню мережу з нашого IP, і без входу це відкритий проксі для будь-кого.

### Ключі AI-провайдерів

Ключ шифрується AES-256-GCM і в такому вигляді лежить у `user_ai_keys`.
GCM, а не CBC: він одразу дає тег автентичності, тож підмінений рядок у базі
впаде на розшифруванні, а не поверне сміття, яке потім піде в мережу як «ключ».

Таблиця має увімкнений RLS **без жодної політики** — рядки доступні лише
сервісному ключу. Клієнт отримує ключі виключно через `/api/keys` і завжди
без секрету: у відповіді лишається тільки підказка на кшталт `••••a1b2`.

Поле введення ключа обгорнуте власною `<form>` і має `autocomplete="new-password"`
([ProviderCard](apps/web/src/components/settings/ProviderCard.tsx)) — і те, і те
проти автозаповнювача, а не заради надсилання. Поля, не обгорнуті у `<form>`,
Chrome групує в одну «форму входу» на всю сторінку: єдине поле-пароль ставало
паролем, а найближче текстове поле — логіном, тому в пошук моделі підставлявся
email акаунта, а в поле ключа — збережений пароль. `autocomplete="off"` для
полів-паролів Chrome навмисно зневажає, `new-password` — ні: воно означає «тут
чекають новий секрет, а не збережений». Сторонні менеджери читають власні
позначки відмови (`data-1p-ignore`, `data-lpignore`, `data-form-type`), тому
стоять і вони — тут, і в полі пошуку [Combobox](apps/web/src/components/ui/Combobox.tsx).

### Міграція локальних сесій

Сесії з версії без акаунтів лишилися в `localStorage`. Головна сторінка
показує банер із пропозицією перенести їх в акаунт
([ImportLocalBanner](apps/web/src/components/sessions/ImportLocalBanner.tsx)).
Мовчки переносити не можна: сесії могли створюватися на спільному компʼютері,
і привʼязати їх до чужого акаунта гірше, ніж не перенести взагалі.

Читання йде через [sessionMigration.ts](apps/web/src/services/sessionMigration.ts) —
типи TypeScript у рантаймі нічого не гарантують, а в сховищі лежать дані,
записані попередніми версіями коду. Зміна формату ТЗ це показала жорстко:
стара сесія дала **чорний екран** — `SourceBadge` не знайшов `meta.source`
(зʼявився разом із каскадом), а `Instruction` — `brief.instruction`.

Те саме стосується й бази: `jsonb` не має версії формату, тому `getSession()`
звіряє збережений бриф із `seoBriefSchema` і, якщо той не проходить, прибирає
його разом із виставленням `legacy_brief_removed`. Так само самолікується
`has_brief` у списку сесій.

- **Аналізи відновлюються чесно.** Старим сторінкам дописується
  `source: "direct"` — це не припущення: до появи каскаду інших способів
  завантаження не існувало.
- **Старе ТЗ відкидається.** Синтезувати англійські інструкції та блоки без AI
  неможливо, тому бриф прибирається, а сесія лишається з результатами
  парсингу — перегенерація в один клік і без повторного завантаження сторінок.
- **Причина показується користувачеві** і не зникає після перезавантаження:
  прапорець `legacyBriefRemoved` живе в сесії, доки не згенеровано нове ТЗ.

Понад це стоїть [ErrorBoundary](apps/web/src/components/ErrorBoundary.tsx):
одна помилка рендеру більше не гасить увесь застосунок. Повна відмова
інтерфейсу — надто дорога ціна за один невірний доступ до поля.

### Що запускається саме, а що за кнопкою

Аналіз URL стартує автоматично для щойно створеної сесії. Генерація ТЗ —
навмисно за кнопкою: вона витрачає токени, і автозапуск на кожному
перезавантаженні сторінки був би неприємним сюрпризом.

Та сама межа у власній сторінці: парсинг стартує сам, щойно в сесії зʼявилася
адреса — байдуже, вказали її при створенні чи додали пізніше, — а саме
порівняння чекає кнопки. Парсинг безкоштовний, і без нього порівнювати нічого;
порівняння витрачає токени.

Кожен URL відправляється окремим запитом, хоча `/api/analyze` приймає масив:
так рядки заповнюються по мірі готовності, а не всі разом після найповільнішої
сторінки.

## Публічне посилання

Сесію можна відкрити для перегляду без входу — щоб віддати ТЗ райтерові або
показати звіт клієнтові. Посилання виглядає як `/p/<token>`, де токен — 16
випадкових байтів у base64url (22 символи). Це і є весь контроль доступу, тому
токен генерується `randomBytes`, а не з id сесії: id не секрет і зайве
розкриває внутрішній ідентифікатор.

```text
services/shares/repository.ts  рядок session_shares: читання, запис, видалення
services/shares/snapshot.ts    зліпок і його zod-схема
services/shares/publish.ts     публікація: сесія → зліпок → рядок
routes/public.ts               GET /api/public/shares/:token — без входу
components/share/SharePanel.tsx        публікація на сторінці сесії
components/share/SharedPageList.tsx    сторінки в публічній версії
pages/PublicSharePage.tsx              сама сторінка /p/:token
```

### Публікується зліпок, а не сесія

Сесія — робоче місце: у ній перезапускають аналіз, перегенеровують ТЗ і правлять
його через чат. Якби посилання читало сесію напряму, кожна така дія моментально
змінювала б те, що бачить клієнт, — включно з проміжними станами, яких
показувати не збиралися. Тому вміст замерзає в `session_shares.snapshot`, а
оновлюється окремою кнопкою.

Ціна рішення — зліпок дублює дані сесії, тобто рядок може важити стільки ж,
скільки весь її розібраний контент. Прийнятно: публікують одиниці сесій, і
`getSession()` цей jsonb не читає ніколи — сторінці сесії потрібні лише
посилання й дати, тому `readShare()` не бере колонку `snapshot` у `select`.

**Токен при оновленні не змінюється.** Це головна вимога до «Оновити публічну
версію»: посилання вже могли надіслати, і новий токен на кожне оновлення
означав би мертве посилання в чужій переписці. Тому запис — не `upsert`
(він писав би в рядок новий токен разом з усім іншим), а перевірене `update`
наявного рядка з `insert` як запасним шляхом.

**«Прибрати з публічного» вбиває саме посилання.** Рядок видаляється разом із
токеном, тому наступна публікація дасть іншу адресу. Це навмисно: «прибрати»
має означати «стару адресу вже не відкрити», а не «поки що приховано».

### Що входить

ТЗ — завжди, коли існує: воно і є результат роботи. Решта — за галочками при
публікації:

- **Сторінки конкурентів** — ті самі, що пішли в основу ТЗ. Фільтр — спільний
  `isUsable()` з [@brief/shared](packages/shared/src/utils/analyses.ts), а не
  власна копія умови на сервері: сторінка, виключена вручну, не годиться як
  зразок, і показувати її клієнтові як джерело тим паче нема сенсу. Сторінки з
  помилкою парсингу не входять узагалі — для читача це інформація лише про те,
  що частина роботи не вийшла.
- **Моя сторінка і звіт порівняння** — адреса, розібраний контент, бал і план дій.

Чату немає ніколи, і це вирішується не в інтерфейсі, а в самому зліпку: у
`ShareSnapshot` поля для повідомлень просто не існує.

Вкладки публічної сторінки будуються з вмісту зліпка, а не з вибору автора:
розділ, який він увімкнув, міг лишитися порожнім, і вкладка без нічого гірша за
її відсутність. Єдина вкладка не показується взагалі.

### Зліпок збирає сервер

Тіло `PUT /api/sessions/:id/share` містить лише дві булеві галочки. Приймати
готовий зліпок від клієнта означало б, що за своїм публічним посиланням можна
опублікувати будь-що — від чужого тексту до розмітки. Тому вміст береться з
тієї сесії, якою користувач володіє, а `getSession()` усередині публікації —
не зайва вага, а сама суть операції: він же перевіряє власника й відкидає ТЗ у
застарілому форматі.

Назад повертається лише `SessionShare` (токен і дати), а не оновлена сесія:
вона важить стільки ж, скільки весь розібраний контент, а змінилася тут тільки
публічна версія.

### «Є зміни після публікації»

`session_shares.captured_at` — це `updated_at` сесії на момент зліпка. Свіжіший
`updated_at` означає, що опубліковане відстало, і сторінка сесії показує це
поряд із посиланням. Точніше не рахується навмисно: усе, що змінює `updated_at`,
змінює й те, що пішло б у новий зліпок, а дрібніший облік («ТЗ те саме,
змінилася лише мова») давав би повідомлення, яке іноді бреше.

Одна тонкість у клієнті: `patch()` в [useSession](apps/web/src/hooks/useSession.ts)
за замовчуванням ставить `updatedAt` у поточний час, і після публікації сесія
одразу вважалася б застарілою — на кілька мілісекунд різниці між годинником
браузера й базою. Тому публікація перебиває `updatedAt` датою з відповіді, а
`patch()` дозволяє це зробити (`compute()` застосовується після дефолту).

### Доступ

`routes/public.ts` — єдиний роутер без `requireAuth`, і саме тому він один і
окремий. У решті захист підключається всередині роутера, тож додати маршрут і
забути про нього неможливо; тут навпаки — сам факт, що обробник лежить у цьому
файлі, означає «доступно всім».

`session_shares` має RLS із політикою лише для власника (через сесію, як
`session_analyses`). Політики для `anon` немає, і це не пропуск: публічна
сторінка читає зліпок через API сервісним ключем. Відкрити таблицю анонімній
ролі означало б дати перебір по всіх опублікованих сесіях — токен захищає
конкретне посилання, а не список посилань.

Формат токена перевіряється до запиту в базу: у маршрут без авторизації
приходить будь-що, і сотні символів сміття не мають ставати запитом. Відповідь
для «не існує» і «прибрали з публічного» однакова — за різницею можна було б
перебором дізнатися, які токени колись існували.

`index.html` віддає `robots: noindex, nofollow` на весь застосунок. Головна
причина — саме публічні посилання: секретність токена і є контроль доступу, і
потрапляння такої адреси в індекс скасовувало б її.

### Зліпок у застарілому формату

`jsonb` не має версії формату — та сама проблема, що зі збереженим ТЗ. Тому
`readPublicShare()` звіряє зліпок із `shareSnapshotSchema` і на розходженні
віддає 410 з проханням попросити автора натиснути «Оновити публічну версію»
(посилання при цьому не зміниться). Без цієї перевірки читач отримав би чорний
екран на першому ж доступі до поля, якого в зліпку немає.

## Важливо про tsconfig сервера

Nitro генерує свій tsconfig зі **`"strict": false`**. Це не косметика: без
`strictNullChecks` zod виводить усі поля як опціональні (бо `undefined extends
string` стає `true`), а `string | null` згортається до `string` — і типізація
валідації перетворюється на фікцію, хоча `pnpm typecheck` проходить зелено.
Тому [apps/server/tsconfig.json](apps/server/tsconfig.json) перекриває цей
параметр явно. Не прибирайте його.

## Пастка Windows

Не редагуйте файли проєкту через `Set-Content -Encoding UTF8` у PowerShell 5.1 —
воно дописує BOM, і `package.json` після цього не парситься rollup-ом
(`Unexpected token '﻿'`). Якщо треба з консолі:

```powershell
[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))
```
